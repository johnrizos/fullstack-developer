# Build, Signing & Play Store

Έγραψες το app. Τώρα πρέπει να το **στείλεις** σε πραγματικούς χρήστες. Αυτό σημαίνει: το **Gradle** build system που μεταγλωττίζει & πακετάρει, **build variants** (debug vs release, dev vs prod), **signing** (κρυπτογραφική υπογραφή ώστε το Play Store να εμπιστεύεται τα updates σου), **R8** shrinking (μικρότερο/γρηγορότερο app), το **Android App Bundle** format, και το **Play Console** release flow με staged rollout.

Είναι το κομμάτι που ένας beginner αγνοεί μέχρι την ημέρα του launch — και μετά κολλάει. Ας το ξεκαθαρίσουμε από πριν.

## Τι πρέπει να μπορείς στο τέλος

- να εξηγείς τι κάνει το **Gradle** και τι είναι τα **build variants**,
- να καταλαβαίνεις **versioning** (`versionCode` vs `versionName`),
- να εξηγείς **app signing** και γιατί το keystore είναι κρίσιμο,
- να ξέρεις τι κάνει το **R8/ProGuard** (shrinking, obfuscation) και τους κινδύνους,
- να ξεχωρίζεις **APK vs AAB** (App Bundle),
- να περιγράφεις το **Play Console release flow** (tracks, staged rollout).

## Gradle — το build system

Το **Gradle** είναι το build tool του Android: μεταγλωττίζει Kotlin, ενσωματώνει resources, τρέχει το R8, και παράγει το τελικό package. Το ρυθμίζεις σε `build.gradle.kts` (Kotlin DSL) αρχεία:

```kotlin
android {
    namespace = "com.example.shop"
    compileSdk = 35

    defaultConfig {
        applicationId = "com.example.shop"   // μοναδικό ID στο Play Store — ΔΕΝ αλλάζει ποτέ
        minSdk = 24                            // παλαιότερη υποστηριζόμενη Android έκδοση
        targetSdk = 35
        versionCode = 12                       // ακέραιος, αυξάνει σε ΚΑΘΕ release
        versionName = "1.4.0"                  // string που βλέπει ο χρήστης
    }
}

dependencies {
    implementation("androidx.compose.material3:material3:...")
    // ...
}
```

- Οι **dependencies** δηλώνονται εδώ (το Gradle τις κατεβάζει από Maven repos).
- Το **`applicationId`** είναι η μοναδική ταυτότητα του app στο Play Store — αν το αλλάξεις, γίνεται **άλλο app**.

## Versioning — `versionCode` vs `versionName`

Δύο διαφορετικά πράγματα, συχνό σημείο σύγχυσης:

| | `versionCode` | `versionName` |
|---|---|---|
| Τύπος | ακέραιος (π.χ. `12`) | string (π.χ. `"1.4.0"`) |
| Ποιος το βλέπει | το **σύστημα/Play Store** | ο **χρήστης** |
| Κανόνας | αυξάνει σε **κάθε** upload | ό,τι θέλεις (semver συνήθως) |

> Το Play Store χρησιμοποιεί το **`versionCode`** για να καταλάβει «ποιο είναι νεότερο». Αν ανεβάσεις build με ίδιο ή μικρότερο `versionCode`, το Play **το απορρίπτει**. Το `versionName` είναι απλώς ετικέτα για ανθρώπους. Κλασική interview ερώτηση: «ποια διαφορά;».

## Build variants — debug vs release

Το Gradle παράγει διαφορετικά **variants** από **build types** και **product flavors**:

- **Build types:** `debug` (debuggable, χωρίς shrinking, debug signing) vs `release` (optimized, R8, signed με το πραγματικό σου key).
- **Product flavors** (προαιρετικά): π.χ. `dev`/`prod` με διαφορετικό API URL, ή `free`/`paid`.

```kotlin
buildTypes {
    release {
        isMinifyEnabled = true          // ενεργοποιεί R8
        proguardFiles(getDefaultProguardFile("proguard-android-optimize.txt"), "proguard-rules.pro")
        signingConfig = signingConfigs.getByName("release")
    }
}
```

> Ποτέ μη στέλνεις **debug** build στο store: είναι μεγαλύτερο, πιο αργό, χωρίς obfuscation, και υπογεγραμμένο με το κοινό debug key. Το **release** variant είναι το production artifact.

## App signing — το keystore

Κάθε Android app **υπογράφεται** κρυπτογραφικά. Η υπογραφή αποδεικνύει ότι ένα update προέρχεται από **τον ίδιο** developer — το Android **αρνείται** να εγκαταστήσει update αν η υπογραφή δεν ταιριάζει με την εγκατεστημένη έκδοση.

- Το **keystore** (`.jks`) περιέχει το ιδιωτικό σου κλειδί.
- Υπογράφεις το release build με αυτό.

> **Κρίσιμο:** αν **χάσεις** το keystore (ή το password), **δεν μπορείς πια να ανεβάσεις updates** στο ίδιο app — ποτέ. Θα έπρεπε να δημοσιεύσεις νέο app και να χάσεις όλους τους χρήστες/reviews. Γι' αυτό υπάρχει το **Play App Signing**: ανεβάζεις έναν *upload key*, και η Google κρατά/διαχειρίζεται το πραγματικό *app signing key* — αν χάσεις το upload key, η Google σε βοηθά να το επαναφέρεις. Backup του keystore σε ασφαλές μέρος είναι υποχρεωτικό.

## R8 / ProGuard — shrinking & obfuscation

Το **R8** (ο διάδοχος του ProGuard, ενσωματωμένος στο build) κάνει τρία πράγματα στο release build:

1. **Shrinking (tree-shaking):** αφαιρεί κώδικα & resources που δεν χρησιμοποιούνται → μικρότερο app.
2. **Obfuscation:** μετονομάζει κλάσεις/μεθόδους σε `a`, `b`, `c` → δυσκολότερο reverse-engineering, μικρότερο.
3. **Optimization:** inlining, dead-code elimination → γρηγορότερο.

Ο κίνδυνος: το R8 μπορεί να αφαιρέσει ή να μετονομάσει κώδικα που χρειάζεται **reflection** (π.χ. JSON parsing βάσει ονομάτων πεδίων). Γι' αυτό υπάρχουν **keep rules** στο `proguard-rules.pro`:

```
-keep class com.example.shop.model.** { *; }   # μη μετονομάζεις τα data models
```

> Πρακτικός κίνδυνος: το app δουλεύει τέλεια σε **debug** αλλά **κρασάρει μόνο σε release** — σχεδόν πάντα λείπει ένα keep rule (το R8 πείραξε κάτι που το reflection ψάχνει με το όνομα). Πάντα **δοκίμασε το release build** πριν το ανεβάσεις. Οι σύγχρονες βιβλιοθήκες (Retrofit, Room, serialization) φέρνουν τα δικά τους consumer rules, αλλά ο δικός σου reflection-based κώδικας χρειάζεται προσοχή.

## APK vs AAB (Android App Bundle)

- **APK** (`.apk`): το κλασικό installable package — περιέχει κώδικα & resources για **όλες** τις αρχιτεκτονικές/πυκνότητες. Μεγάλο.
- **AAB** (`.aab`, Android App Bundle): το format που **απαιτεί** πλέον το Play Store για νέα apps. Ανεβάζεις **ένα** bundle· η Google παράγει **βελτιστοποιημένα APKs ανά συσκευή** (σωστό ABI, density, γλώσσα) — ο χρήστης κατεβάζει μόνο ό,τι χρειάζεται η συσκευή του → **μικρότερο download**.

> Στη συνέντευξη: «AAB = ανεβάζεις ένα bundle, η Google κάνει split σε per-device APKs (Dynamic Delivery)· το Play απαιτεί AAB για νέα apps από το 2021». Για sideloading/άλλα stores μπορεί ακόμα να χρειάζεσαι APK.

## Play Console release flow

Δημοσιεύεις μέσω του **Play Console**, με **tracks** (κανάλια δοκιμής πριν το production):

```
internal  →  closed (alpha)  →  open (beta)  →  production
(ομάδα)      (testers)          (public opt-in)   (όλοι)
```

Στο production κάνεις **staged rollout**: κυκλοφορείς σε **ποσοστό** χρηστών (π.χ. 10%), παρακολουθείς crash rate/reviews, και αν όλα καλά **αυξάνεις** σταδιακά στο 100% — αλλιώς **halt** το rollout πριν επηρεαστούν όλοι.

Πριν το production, το app περνά **Play review** (policy/security). Απαιτούνται επίσης store listing (screenshots, περιγραφή), content rating, privacy policy, και data safety form.

> Το mental model σαν deployment strategy (canary): μην πετάς ένα νέο build σε 100% των χρηστών μεμιάς. Staged rollout + crash monitoring (π.χ. Crashlytics/Sentry — είδαμε παρόμοιο στο RN production) σου δίνει δίχτυ ασφαλείας.

## Πώς απαντάς στη συνέντευξη

> «Walk me through shipping an Android app to production.»

> Gradle is the build system — it compiles Kotlin, bundles resources, runs R8, and produces the artifact, configured in `build.gradle.kts`. I ship the `release` variant, not debug: it's minified, optimized, and signed with my real key. Versioning has two parts people mix up — `versionCode` is an integer the Play Store uses to tell which build is newer, so it must increase on every upload, while `versionName` is just the human-facing string. Every app is cryptographically signed, and Android refuses an update whose signature doesn't match, so the keystore is critical — lose it and you can't update the app ever, which is exactly why I use Play App Signing, where Google manages the real signing key and I upload with an upload key. R8 shrinks, obfuscates, and optimizes the release build; the classic gotcha is a crash that only happens in release because R8 renamed something reflection relies on, so I add keep rules and always test the release build before uploading. I upload an Android App Bundle, not an APK — the Play Store requires it for new apps and generates optimized per-device APKs so users download less. Finally I release through Play Console tracks — internal, closed, open, then production — with a staged rollout to a small percentage first while I watch crash rates, ready to halt before it reaches everyone.
