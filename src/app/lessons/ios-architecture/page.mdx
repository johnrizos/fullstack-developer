# Architecture & MVVM

Μέχρι τώρα έχεις views, state, navigation και ένα data layer. Το ερώτημα αρχιτεκτονικής είναι: **πού μπαίνει η λογική;** Αν στριμώξεις networking, business rules και formatting μέσα στα views, καταλήγεις σε «massive views» που δεν δοκιμάζονται και δεν επαναχρησιμοποιούνται. Η κυρίαρχη απάντηση στο SwiftUI είναι το **MVVM** (Model–View–ViewModel), υλοποιημένο καθαρά με το `@Observable` macro.

## Τι πρέπει να μπορείς στο τέλος

- να χωρίζεις μια feature σε **layers** (UI / domain / data),
- να γράφεις ένα `@Observable` **ViewModel** και να ξέρεις τι μπαίνει μέσα του,
- να εφαρμόζεις **unidirectional data flow** (view → intent → state → view),
- να κάνεις **dependency injection** για testability,
- να καταλαβαίνεις τον **App/Scene lifecycle**,
- να αναγνωρίζεις τα anti-patterns (massive views, λογική στο body).

## Layers — διαχωρισμός ευθυνών

Μια υγιής feature χωρίζεται σε τρία στρώματα:

| Layer | Ευθύνη | Παράδειγμα |
|---|---|---|
| **UI (View)** | Πώς φαίνονται τα δεδομένα, χειρισμός input | SwiftUI views, modifiers |
| **Domain (ViewModel)** | Κατάσταση οθόνης, business rules, ενέργειες | `@Observable` ViewModel |
| **Data (Repository)** | Από πού έρχονται τα δεδομένα | Repository, API, SwiftData |

Ο κανόνας: **οι εξαρτήσεις δείχνουν προς τα μέσα.** Το View ξέρει το ViewModel· το ViewModel ξέρει το Repository (μέσω protocol)· το Repository δεν ξέρει τίποτα για UI. Έτσι κάθε layer δοκιμάζεται και αλλάζει ανεξάρτητα.

## Το ViewModel — `@Observable`

Το ViewModel κρατά την **κατάσταση της οθόνης** και τις **ενέργειες** που τη μεταβάλλουν. Στο σύγχρονο SwiftUI είναι μια `@Observable` class, συνήθως `@MainActor`:

```swift
@MainActor
@Observable
final class ProductListViewModel {
    // κατάσταση που «βλέπει» το view
    private(set) var products: [Product] = []
    private(set) var isLoading = false
    private(set) var errorMessage: String?

    // εξάρτηση μέσω protocol (DI)
    private let repository: ProductRepository

    init(repository: ProductRepository) {
        self.repository = repository
    }

    // intent / action
    func load() async {
        isLoading = true
        defer { isLoading = false }
        do {
            products = try await repository.products()
            errorMessage = nil
        } catch {
            errorMessage = "Αποτυχία φόρτωσης"
        }
    }
}
```

Το view γίνεται **λεπτό** — μόνο παρουσίαση:

```swift
struct ProductListView: View {
    @State private var vm: ProductListViewModel

    init(repository: ProductRepository) {
        _vm = State(initialValue: ProductListViewModel(repository: repository))
    }

    var body: some View {
        List(vm.products) { Text($0.title) }
            .overlay { if vm.isLoading { ProgressView() } }
            .task { await vm.load() }   // ξεκινά όταν εμφανίζεται, ακυρώνεται όταν φεύγει
    }
}
```

> Τα `private(set)` properties σημαίνουν: το view **διαβάζει** την κατάσταση, αλλά **μόνο** το ViewModel τη γράφει. Έτσι όλες οι αλλαγές περνούν από ελεγχόμενες actions — δεν μπορεί ένα view να αλλάξει «κρυφά» το state.

## Unidirectional data flow

Η ροή είναι μονόδρομη και προβλέψιμη:

1. **View** εμφανίζει state (`vm.products`).
2. Ο χρήστης κάνει μια ενέργεια → το view καλεί ένα **intent** (`vm.load()`, `vm.delete(id)`).
3. Το **ViewModel** εκτελεί τη λογική, μιλά στο repository, και ενημερώνει το **state**.
4. Η αλλαγή state → το SwiftUI ξανα-renderάρει το **View**.

Ποτέ δεν πηγαίνει το view να μεταλλάξει state κατευθείαν ή να καλέσει το repository. Αυτό είναι το ίδιο μοτίβο με MVVM+UDF στο Android (Compose) και με Redux-style flows στο web.

## Dependency injection

Πρόσεξε ότι το ViewModel παίρνει το `repository` στον `init` ως **protocol**, δεν το φτιάχνει το ίδιο. Αυτό είναι **dependency injection**, και είναι το κλειδί για **testability**:

```swift
// Production
ProductListView(repository: DefaultProductRepository(...))

// Test / Preview
struct MockRepo: ProductRepository {
    func products() async throws -> [Product] { [Product(id: "1", title: "Test", price: 1)] }
}
let vm = ProductListViewModel(repository: MockRepo())
```

Επειδή η εξάρτηση είναι protocol, στα unit tests περνάς mock που επιστρέφει σταθερά δεδομένα (ή πετάει error για να τεστάρεις το error state) — **χωρίς δίκτυο**. Το ίδιο κάνει τα SwiftUI Previews γρήγορα και ντετερμινιστικά.

## App & Scene lifecycle

Η είσοδος της app είναι ένα struct με `@main` που conform-άρει στο `App`:

```swift
@main
struct ShopApp: App {
    var body: some Scene {
        WindowGroup {
            RootView()
        }
        .modelContainer(for: ProductEntity.self)   // SwiftData store
    }
}
```

- **`App`** = ολόκληρη η εφαρμογή· το `body` επιστρέφει **Scenes**.
- **`Scene`** (π.χ. `WindowGroup`) = ένα «παράθυρο» UI. Σε iPhone συνήθως ένα· σε iPad/Mac πολλά.
- Στη ρίζα στήνεις global πράγματα: `.modelContainer`, `.environment(...)` για shared session/theme.
- Την κατάσταση foreground/background/inactive τη διαβάζεις με `@Environment(\.scenePhase)` (π.χ. «αποθήκευσε όταν πάει background»).

> Σε αντίθεση με το UIKit `AppDelegate`, το SwiftUI lifecycle είναι declarative. Για ειδικές ανάγκες (push notifications setup) υπάρχει `@UIApplicationDelegateAdaptor`, αλλά τα βασικά τα καλύπτει το `App`/`Scene`/`scenePhase`.

## Anti-patterns

- **Massive view:** networking, formatting, business logic στο `body`. → Βγάλ' τα σε ViewModel.
- **Λογική στο computed `body`:** το `body` πρέπει να είναι **καθαρή** παρουσίαση· βαριοί υπολογισμοί εκεί τρέχουν σε κάθε re-render.
- **View που φτιάχνει τις εξαρτήσεις του:** `URLSession`/repository μέσα στο view → αδύνατο να τεσταριστεί. Κάνε inject.
- **Διπλή κατάσταση:** ίδια πληροφορία σε view και ViewModel που ξεσυγχρονίζεται. Ένας ιδιοκτήτης.
- **ViewModel που ξέρει από SwiftUI:** το ViewModel δεν πρέπει να importάρει views ή να χειρίζεται navigation UI· κρατά state & logic, καθαρό και testable.

## Πώς απαντάς στη συνέντευξη

> «How do you structure a SwiftUI feature, and why MVVM?»

> I split a feature into layers: the view handles presentation and input, an `@Observable` view model owns the screen's state and business logic, and a repository (behind a protocol) owns where data comes from. Dependencies point inward — the view knows the view model, the view model knows the repository, and the repository knows nothing about UI. The view model is a `@MainActor @Observable` class exposing `private(set)` state that only it can mutate, plus intents like `load()`; the view just reads state and calls intents, which gives unidirectional data flow. I inject the repository as a protocol into the view model's init, so in tests and previews I pass a mock that returns fixed data or throws — no network, fully deterministic. The app entry is a `@main App` returning `Scene`s, where I set up the model container and shared environment, and I read foreground/background transitions via `scenePhase`. The anti-pattern I avoid is the massive view — logic in `body` that can't be tested and reruns on every render; MVVM keeps the view thin.
