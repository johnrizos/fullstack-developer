# Data & Networking

Μια πραγματική app φέρνει δεδομένα από το δίκτυο, τα αποθηκεύει τοπικά, και δουλεύει ακόμα και offline. Σε αυτό το μάθημα ενώνουμε τρία κομμάτια: **URLSession** με async/await για REST, **Codable** για JSON, και **SwiftData** για local persistence — και τα δένουμε με το **repository pattern** ώστε το UI να μη νοιάζεται από πού έρχονται τα δεδομένα.

## Τι πρέπει να μπορείς στο τέλος

- να κάνεις network requests με `URLSession` + async/await,
- να κάνεις (de)serialize JSON με `Codable`,
- να χειρίζεσαι HTTP status & errors σωστά,
- να αποθηκεύεις τοπικά με **SwiftData** (`@Model`),
- να εφαρμόζεις το **repository pattern** και **single source of truth**,
- να σχεδιάζεις **offline-first** ροή δεδομένων.

## `URLSession` + async/await

Το built-in `URLSession` κάνει HTTP. Με το async μοντέλο, ένα GET είναι λίγες γραμμές:

```swift
func fetchProducts() async throws -> [Product] {
    let url = URL(string: "https://api.example.com/products")!
    let (data, response) = try await URLSession.shared.data(from: url)

    guard let http = response as? HTTPURLResponse, (200..<300).contains(http.statusCode) else {
        throw APIError.badStatus
    }
    return try JSONDecoder().decode([Product].self, from: data)
}
```

- Το `data(from:)` επιστρέφει `(Data, URLResponse)` — **πάντα** ελέγχεις το `HTTPURLResponse.statusCode`· ένα 404/500 **δεν** πετάει από μόνο του, απλώς επιστρέφει data.
- Για POST/PUT φτιάχνεις `URLRequest`, θέτεις `httpMethod`, headers και `httpBody`.

## `Codable` — JSON ↔ Swift types

Το `Codable` (= `Decodable` + `Encodable`) κάνει αυτόματο (de)serialization. Δηλώνεις το type να το conform-άρει και τελείωσες:

```swift
struct Product: Codable, Identifiable {
    let id: String
    let title: String
    let price: Double
}

let product = try JSONDecoder().decode(Product.self, from: data)   // JSON → Swift
let body    = try JSONEncoder().encode(product)                    // Swift → JSON
```

Όταν τα ονόματα JSON διαφέρουν από τα Swift (π.χ. `product_title` → `title`), χρησιμοποιείς `CodingKeys`:

```swift
struct Product: Codable {
    let id: String
    let title: String
    enum CodingKeys: String, CodingKey {
        case id
        case title = "product_title"
    }
}
```

Ή, για snake_case παντού: `decoder.keyDecodingStrategy = .convertFromSnakeCase`.

> **DTO vs domain:** συχνά ο τύπος που ταιριάζει το JSON (DTO) δεν είναι ο τύπος που θέλει το UI. Είναι ΟΚ να αποκωδικοποιείς σε ένα DTO struct και μετά να το χαρτογραφείς στο domain model σου — κρατά το UI ανεξάρτητο από το σχήμα του API.

## `SwiftData` — local persistence

Το **SwiftData** (iOS 17+, ο διάδοχος του Core Data) αποθηκεύει αντικείμενα τοπικά με ελάχιστο κώδικα. Σημειώνεις μια class με `@Model`:

```swift
import SwiftData

@Model
final class ProductEntity {
    @Attribute(.unique) var id: String
    var title: String
    var price: Double
    init(id: String, title: String, price: Double) {
        self.id = id; self.title = title; self.price = price
    }
}
```

Στήνεις το container στη ρίζα και δουλεύεις μέσα από ένα `ModelContext`:

```swift
// App entry
.modelContainer(for: ProductEntity.self)

// Μέσα σε view — αυτόματα ενημερώνεται όταν αλλάξει το store
@Query private var products: [ProductEntity]
@Environment(\.modelContext) private var context

context.insert(ProductEntity(id: "1", title: "Καφές", price: 3.5))
try context.save()
```

Το `@Query` είναι το εντυπωσιακό: διαβάζει από το store και **ξανα-renderάρει αυτόματα** το view όταν αλλάξουν τα δεδομένα — reactive persistence.

## Repository pattern — μία πηγή αλήθειας

Αν τα views καλούν κατευθείαν `URLSession` και `SwiftData`, η λογική δεδομένων σκορπίζεται παντού. Το **repository** συγκεντρώνει το «από πού έρχονται τα δεδομένα» πίσω από ένα καθαρό interface (protocol):

```swift
protocol ProductRepository {
    func products() async throws -> [Product]
}

final class DefaultProductRepository: ProductRepository {
    private let api: APIClient
    private let context: ModelContext

    func products() async throws -> [Product] {
        do {
            let fresh = try await api.fetchProducts()   // 1. δίκτυο
            cache(fresh)                                // 2. γράψε στο SwiftData
            return fresh
        } catch {
            return cachedProducts()                     // 3. offline → τοπικά
        }
    }
}
```

Το UI ζητά `repository.products()` και **δεν ξέρει** αν ήρθαν από το δίκτυο ή το cache. Αυτό είναι το **single source of truth**: το local store είναι η αλήθεια που βλέπει το UI, και το δίκτυο απλώς το **ανανεώνει**.

## Offline-first

Η ιδέα: **το UI διαβάζει πάντα από το local store· το δίκτυο ενημερώνει το store στο παρασκήνιο.** Ροή:

1. Άνοιγμα οθόνης → δείξε αμέσως ό,τι υπάρχει τοπικά (instant, ακόμα κι offline).
2. Ξεκίνα network refresh.
3. Επιτυχία → γράψε στο store → το `@Query` ενημερώνει το UI αυτόματα.
4. Αποτυχία → κράτα τα cached δεδομένα, δείξε διακριτικό indicator.

> Πλεονεκτήματα: η app δείχνει περιεχόμενο **αμέσως** (χωρίς spinner σε κάθε άνοιγμα), δουλεύει σε τούνελ/αεροπλάνο, και είναι ανθεκτική σε flaky δίκτυο. Η τιμή που πληρώνεις είναι **cache invalidation / conflict handling** — πρέπει να αποφασίσεις πότε τα cached δεδομένα είναι «μπαγιάτικα» και τι γίνεται όταν local & remote διαφωνούν.

## Loading & error states στο UI

Μοντελοποίησε ρητά τις καταστάσεις (θυμήσου το enum με associated values):

```swift
enum LoadState<T> {
    case loading
    case loaded(T)
    case failed(String)
}
```

Έτσι το view δείχνει spinner / δεδομένα / μήνυμα λάθους — καθαρά, χωρίς σκόρπια boolean flags (`isLoading`, `hasError`) που μπερδεύονται.

## Πώς απαντάς στη συνέντευξη

> «How would you architect networking and local data in a SwiftUI app?»

> I do networking with `URLSession` and async/await, and I always check the `HTTPURLResponse` status because a 404 or 500 doesn't throw — it just returns data. I decode JSON with `Codable`, using `CodingKeys` when the API field names differ, and I'll often decode into a DTO and map to a domain model so the UI isn't coupled to the API shape. For local persistence I use SwiftData with `@Model`, and `@Query` in the view so the UI re-renders automatically whenever the store changes. I tie it together with a repository behind a protocol: the view asks the repository for data and doesn't know whether it came from the network or the cache. That gives me a single source of truth and makes it testable with a mock repo. The overall flow is offline-first — the UI reads from the local store so it shows content instantly and works offline, while the network refreshes the store in the background. The trade-off I'm explicit about is cache invalidation and conflict handling.
