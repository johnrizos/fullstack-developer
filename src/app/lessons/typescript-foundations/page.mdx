# TypeScript Foundations

Το TypeScript είναι JavaScript με στατικό type checking — τα types εξαφανίζονται στο compile, άρα **δεν** αλλάζουν τη runtime συμπεριφορά. Η αξία του: πιάνει λάθη πριν τρέξει ο κώδικας, τεκμηριώνει contracts μεταξύ modules, και κάνει το refactoring ασφαλές (μετονομάζεις ένα πεδίο και βλέπεις αμέσως κάθε σπασμένη χρήση). Σε fullstack αγγελίες είναι πλέον σχεδόν υποχρεωτικό. Αυτό το πρώτο μάθημα του track χτίζει τη βάση: πώς σκέφτεται ο compiler, ο **πλήρης κατάλογος** των τύπων, arrays/tuples/objects, `type` vs `interface`, και η κρίσιμη ιδέα ότι **τα types εξαφανίζονται στη runtime**. Τα επόμενα μαθήματα μπαίνουν σε setup/compiler, unions/narrowing, functions, classes, generics, utility/mapped types, safety/config και declarations.

## Βασικοί τύποι & annotations

Δηλώνεις τον τύπο μιας μεταβλητής/παραμέτρου με `: Type`. Συχνά δεν χρειάζεται — ο compiler κάνει **inference**:

```ts
let title: string = "Μάθε TS";  // explicit
let count = 0;                  // inferred ως number — δεν χρειάζεται annotation
const tags: string[] = [];      // array από strings
const point: { x: number; y: number } = { x: 1, y: 2 };

function greet(name: string): string {  // typed param + return
  return `Γεια ${name}`;
}
```

Κανόνας: **άσε το inference να δουλέψει** για τοπικές μεταβλητές· βάλε explicit types στα **όρια** — function signatures, public APIs, exported types. Εκεί το type είναι το «συμβόλαιο».

## Ο πλήρης κατάλογος των τύπων

Πριν προχωρήσεις, να όλα όσα μπορείς να γράψεις δεξιά από το `:` — ώστε να μη συναντάς ποτέ έναν τύπο που δεν αναγνωρίζεις:

| Τύπος | Τι είναι | Παράδειγμα |
|---|---|---|
| `string`, `number`, `boolean` | τα τρία primitives που χρησιμοποιείς κάθε μέρα | `let n: number = 3.14` |
| `bigint`, `symbol` | σπάνιοι· τεράστιοι ακέραιοι, μοναδικά κλειδιά | `let big: bigint = 10n` |
| `null`, `undefined` | οι δύο «κενές» τιμές — ξεχωριστοί τύποι με `strictNullChecks` | `let x: string \| null` |
| `T[]` / `Array<T>` | πίνακας | `string[]` |
| `[A, B]` | tuple — σταθερό μήκος & θέση | `[number, string]` |
| `{ a: string }` | object type (inline) | `{ x: number; y: number }` |
| `(a: number) => string` | function type | callbacks |
| `"todo" \| "done"` | literal union — συγκεκριμένες τιμές | status fields |
| `any` | **σβήνει** τον έλεγχο — απόφυγέ το | — |
| `unknown` | «δεν ξέρω ακόμα» — type-safe εκδοχή του any | είσοδος από API |
| `void` | δεν επιστρέφει χρήσιμη τιμή | `function log(): void` |
| `never` | δεν συμβαίνει ποτέ (throw / αδύνατο) | exhaustiveness |
| `object` | οτιδήποτε μη-primitive (σπάνια χρήσιμο) | — |

Δύο διευκρινίσεις που μπερδεύουν αρχάριους: το `number` καλύπτει **και** ακέραιους και δεκαδικούς (δεν υπάρχει `int`/`float`), και το `String`/`Number` με κεφαλαίο είναι τα wrapper objects της JavaScript — **γράφεις πάντα πεζά** (`string`, `number`, `boolean`).

## Arrays, tuples & readonly

```ts
const names: string[] = ["Ada", "Grace"];
const scores: Array<number> = [1, 2];        // ίδιο πράγμα, άλλο συντακτικό
const matrix: number[][] = [[1, 2], [3, 4]]; // πίνακας από πίνακες
const mixed: (string | number)[] = [1, "a"]; // προσοχή στις παρενθέσεις!
```

Ένα **tuple** είναι πίνακας με σταθερό μήκος όπου **κάθε θέση έχει δικό της τύπο** — το χρησιμοποιείς για «ζευγάρια» και για επιστροφές πολλαπλών τιμών (το `useState` της React είναι tuple):

```ts
let pair: [string, number] = ["age", 30];
pair = [30, "age"];                    // ❌ λάθος σειρά

type Coords = [x: number, y: number];  // named members — μόνο για αναγνωσιμότητα
type Result = [ok: boolean, ...errors: string[]]; // rest σε tuple
const [value, setValue] = useState(0); // [number, (n: number) => void]
```

Το `readonly` απαγορεύει τη μετάλλαξη — σε πίνακες και σε properties:

```ts
const list: readonly string[] = ["a", "b"];
list.push("c");                         // ❌ το push δεν υπάρχει σε readonly array

interface User {
  readonly id: string;   // ορίζεται μία φορά, δεν αλλάζει
  name: string;
}
```

Είναι **compile-time** έλεγχος (όχι `Object.freeze`) — αλλά ακριβώς αυτό θέλεις: δηλώνει πρόθεση και πιάνει κατά λάθος μεταλλάξεις πριν τρέξει ο κώδικας.

## Object types: optional, nested, index signatures

```ts
interface Task {
  id: string;
  title: string;
  estimateHours?: number;      // optional → τύπος: number | undefined
  author: {                    // nested object
    id: string;
    name: string;
  };
  tags: string[];
}
```

Ένα **optional property** (`?`) μπορεί να λείπει τελείως· ένα `x: number | undefined` πρέπει να **υπάρχει** αλλά μπορεί να είναι `undefined`. Λεπτή διαφορά που εμφανίζεται όταν φτιάχνεις objects.

Όταν **δεν ξέρεις τα κλειδιά** εκ των προτέρων, χρησιμοποιείς **index signature**:

```ts
interface Translations {
  [key: string]: string;         // οποιοδήποτε string κλειδί → string τιμή
}

const el: Translations = { hello: "Γεια", bye: "Αντίο" };
el.anything;                     // τύπος: string (ο compiler δεν ξέρει αν υπάρχει!)

// Το ίδιο, πιο σύγχρονα, με utility type:
type Translations2 = Record<string, string>;

// Περιορισμένα κλειδιά:
type StatusLabels = Record<"todo" | "doing" | "done", string>; // ΟΛΑ υποχρεωτικά
```

> Παγίδα: με index signature ο compiler υπόσχεται `string` για **κάθε** κλειδί, ακόμα κι αν δεν υπάρχει — άρα `el.typo` περνά και σκάει στη runtime. Το flag `noUncheckedIndexedAccess` (μάθημα *Type Safety*) το διορθώνει προσθέτοντας `| undefined`.

## Ενώνοντας types: `&` και `extends`

Το **intersection** (`&`) συνδυάζει σχήματα — «και το ένα **και** το άλλο»:

```ts
type WithId = { id: string };
type WithTimestamps = { createdAt: Date; updatedAt: Date };

type Task = WithId & WithTimestamps & { title: string };
// έχει: id, createdAt, updatedAt, title
```

Με interfaces το ίδιο γίνεται με `extends` (και δέχεται πολλά):

```ts
interface Entity { id: string }
interface Timestamped { createdAt: Date }
interface Task extends Entity, Timestamped { title: string }
```

Μην το μπερδεύεις με το union (`|`) που σημαίνει «**ένα από** τα δύο». Μνημονικός κανόνας: το `&` **προσθέτει πεδία**, το `|` **προσθέτει επιλογές** (και αφαιρεί ό,τι μπορείς να κάνεις με ασφάλεια, μέχρι να κάνεις narrowing).

## Literal types & widening — γιατί `const` και `let` διαφέρουν

Ο compiler **πλαταίνει** (widening) τον τύπο μιας μεταβλητής που μπορεί να αλλάξει:

```ts
let status = "todo";     // τύπος: string   — μπορείς να του δώσεις οτιδήποτε
const status2 = "todo";  // τύπος: "todo"   — literal type, δεν πρόκειται να αλλάξει
```

Ένας **literal type** είναι μια *συγκεκριμένη τιμή* ως τύπος. Αυτό εξηγεί ένα από τα πιο συχνά μπερδέματα των αρχαρίων:

```ts
type Status = "todo" | "done";

const obj = { status: "todo" };     // το status συμπεραίνεται ως string
const s: Status = obj.status;       // ❌ string δεν είναι assignable σε "todo" | "done"

const obj2 = { status: "todo" } as const;  // ✅ readonly + literal types
```

Το `as const` (αναλυτικά στο μάθημα *Unions & Narrowing*) λέει «κράτα τον **στενότερο** δυνατό τύπο». Ο κανόνας πίσω από όλα: **ό,τι μπορεί να αλλάξει, πλαταίνει**.

## Η βάση: structural typing

Το πιο σημαντικό πράγμα για το πώς σκέφτεται ο compiler: συγκρίνει **σχήματα**, όχι ονόματα. Αυτό λέγεται structural typing (ή «duck typing»):

```ts
interface Point {
  x: number;
  y: number;
}

const spot = { x: 1, y: 2, label: "home" };
const p: Point = spot; // ✅ ΟΚ — έχει ό,τι χρειάζεται το Point (και παραπάνω)

function logPoint(point: Point) {}
logPoint({ x: 1, y: 2 });               // ✅
logPoint({ x: 1, y: 2, label: "hi" });  // ❌ object literal: excess property check!
```

Παρατήρησε την ασυμμετρία — όταν περνάς **object literal απευθείας**, το TypeScript κάνει αυστηρότερο έλεγχο για «έξτρα» properties (πιάνει typos). Μέσω μεταβλητής, αρκεί το σχήμα να καλύπτεται. Αντίθετο μοντέλο: το **nominal typing** (Java/C#), όπου μετράει το όνομα της κλάσης.

## type vs interface — η σίγουρη ερώτηση

Και τα δύο περιγράφουν object shapes. Οι πραγματικές διαφορές:

| | `interface` | `type` |
|---|---|---|
| Object shapes | ✅ | ✅ |
| Unions, primitives, tuples | ❌ | ✅ `type ID = string \| number` |
| Επέκταση | `extends` | `&` (intersection) |
| Declaration merging | ✅ — δηλώσεις με ίδιο όνομα ενώνονται | ❌ — διπλό όνομα = error |

Πρακτικός κανόνας που αρκεί σε συνέντευξη: **interface για δημόσια object contracts** (props, models — και για library types όπου το merging βοηθά), **type για unions και συνθέσεις**. Μέσα σε ένα project, η συνέπεια μετράει περισσότερο από την επιλογή.

## Τα types εξαφανίζονται στη runtime

Η πιο παρεξηγημένη ιδέα — και ερώτηση-φίλτρο. Το TypeScript κάνει **type erasure**: μετά το compile, ο κώδικας είναι σκέτη JavaScript χωρίς κανένα type. Συνέπειες:

- **Μηδενικό runtime κόστος** — τα types δεν υπάρχουν όταν τρέχει ο κώδικας.
- **Δεν μπορείς να ελέγξεις types στη runtime** με τον τρόπο των classes — δεν υπάρχει «`if (x is User)`» μαγικά.
- **Τα δεδομένα από έξω (API/JSON) δεν ελέγχονται** από τους τύπους. Ένα `as User` είναι απλώς υπόσχεση προς τον compiler — γι' αυτό χρειάζεσαι **runtime validation** (το βλέπεις στο safety μάθημα).

```ts
interface User { name: string; }
const raw = '{"username": "ada"}';
const user = JSON.parse(raw) as User; // ψέμα στον compiler — δεν ελέγχει τίποτα
user.name.toUpperCase();              // 💥 runtime: name είναι undefined
```

## Πώς απαντάς στη συνέντευξη

«Why TypeScript, and what's the catch?»

> TypeScript catches type errors at compile time, documents the contracts between modules, and makes refactoring safe — renaming a field shows every broken usage instantly. The compiler is structural: compatibility is about an object's shape, not the name of its type. The catch is that types are erased at compile time — there's no runtime cost, but it also means external data still needs runtime validation; an `as` assertion checks nothing. My rule of thumb on `type` vs `interface`: interfaces for object contracts (they support `extends` and declaration merging), type aliases for unions and compositions — and consistency within a codebase above the choice itself.
