# Java Foundations

Η **Java** είναι από τις πιο διαδεδομένες γλώσσες στον κόσμο — κυριαρχεί σε **enterprise backend** (τράπεζες, μεγάλα συστήματα), τρέχει σε δισεκατομμύρια συσκευές, και το οικοσύστημά της (Spring) είναι το de-facto standard για σοβαρά backend APIs. Είναι **στατικά τυπωμένη**, **object-oriented**, και τρέχει στο **JVM** (Java Virtual Machine) — το ίδιο runtime με την Kotlin που μόλις είδες.

Αν έρχεσαι από την Kotlin, πολλά concepts (JVM, collections, OOP) μεταφέρονται· η Java είναι πιο **verbose** και λιγότερο «magic», αλλά ακριβώς αυτή η ρητότητα είναι που τη θέλουν τα enterprise interviews. Αυτό το μάθημα είναι η γλώσσα & το runtime — τα OOP βάθη έρχονται στο επόμενο.

## Τι πρέπει να μπορείς στο τέλος

- να εξηγείς τι είναι το **JVM** και πώς τρέχει η Java (source → bytecode → JVM),
- να ξεχωρίζεις **compiled + platform-independent** («write once, run anywhere»),
- να διακρίνεις **primitives vs objects** (και το autoboxing),
- να καταλαβαίνεις **static typing** & τη δήλωση τύπων,
- να γράφεις βασική δομή (`class`, `main`, control flow, methods),
- να πιάνεις το OOP mental model («όλα ζουν σε κλάσεις»).

## Πώς τρέχει η Java: source → bytecode → JVM

Σε αντίθεση με τη JavaScript (interpreted) ή τη C (compiled σε native machine code), η Java έχει ένα **δύο-σταδίων** μοντέλο:

```
Foo.java  ──javac──▶  Foo.class (bytecode)  ──JVM──▶  τρέχει σε οποιοδήποτε OS
(source)   compile     (portable)             runtime
```

1. Ο **compiler** (`javac`) μεταγλωττίζει το `.java` source σε **bytecode** (`.class`) — μια ενδιάμεση, φορητή αναπαράσταση.
2. Το **JVM** διαβάζει το bytecode και το τρέχει (με **JIT** compilation σε native code για ταχύτητα).

> Αυτό είναι το «**write once, run anywhere**»: το ίδιο `.class` bytecode τρέχει σε Windows, Linux, macOS — αρκεί να υπάρχει JVM. Το JVM είναι το abstraction πάνω από το OS. Γι' αυτό και η Kotlin (που κάνει compile στο ίδιο bytecode) συνυπάρχει με Java στο ίδιο project.

Ορολογία που μπερδεύει σε interviews:

| Όρος | Τι είναι |
|---|---|
| **JVM** | Το runtime που τρέχει bytecode |
| **JRE** | JVM + βιβλιοθήκες (για να **τρέξεις** Java) |
| **JDK** | JRE + εργαλεία ανάπτυξης (`javac`, debugger) — για να **γράψεις** Java |

## Η δομή ενός Java program

Στην Java, **τα πάντα ζουν μέσα σε κλάση** — δεν υπάρχουν top-level functions όπως στην JS/Python. Το entry point είναι η `main`:

```java
public class Hello {
    public static void main(String[] args) {
        System.out.println("Γεια σου Java");
    }
}
```

- `public class Hello` — κάθε αρχείο έχει (συνήθως) μία public κλάση με το ίδιο όνομα (`Hello.java`).
- `public static void main(String[] args)` — η ακριβής υπογραφή που ψάχνει το JVM για να ξεκινήσει. `static` = ανήκει στην κλάση, όχι σε instance· `void` = δεν επιστρέφει τίποτα· `String[] args` = command-line arguments.
- Κάθε statement τελειώνει με **`;`** και τα blocks μπαίνουν σε **`{ }`**.

## Static typing & δήλωση τύπων

Η Java είναι **statically typed**: κάθε μεταβλητή έχει τύπο γνωστό σε **compile time**, και ο compiler απορρίπτει λάθη τύπων πριν καν τρέξει ο κώδικας.

```java
int count = 5;
String name = "Giannis";
double price = 3.5;
boolean active = true;

// count = "text";   // compile error — δεν ταιριάζει ο τύπος

// Από Java 10+: var για local type inference (ο τύπος συνάγεται, ΠΑΡΑΜΕΝΕΙ static)
var total = count * price;   // ο compiler ξέρει ότι είναι double
```

> Το `var` **δεν** κάνει τη Java dynamic (όπως η JS) — απλώς γλιτώνει το να γράψεις τον τύπο όταν είναι προφανής. Ο τύπος είναι ακόμα σταθερός & compile-checked. Χρήση μόνο σε local variables, όχι σε fields/parameters.

## Primitives vs objects

Η Java έχει **δύο κατηγορίες** τιμών — μια ιδιαιτερότητα που δεν έχει η Kotlin (εκεί όλα φαίνονται objects):

- **Primitives** (πεζά): `int`, `long`, `double`, `boolean`, `char`, `byte`, `short`, `float`. Κρατούν την τιμή **απευθείας**, είναι γρήγορα, **δεν** μπορούν να είναι `null`.
- **Objects / reference types** (κεφαλαία): `String`, `Integer`, `List`, οι δικές σου κλάσεις. Κρατούν **reference** σε αντικείμενο στο heap, μπορούν να είναι `null`.

```java
int a = 5;              // primitive
Integer b = 5;          // wrapper object (autoboxing: int → Integer αυτόματα)
Integer c = null;       // OK — object μπορεί να είναι null
// int d = null;        // compile error — primitive δεν παίρνει null
```

Κάθε primitive έχει το **wrapper class** του (`int`↔`Integer`, `double`↔`Double`). Η μετατροπή γίνεται αυτόματα (**autoboxing/unboxing**). Οι collections (`List<Integer>`) δουλεύουν μόνο με objects, γι' αυτό χρησιμοποιείς τα wrappers εκεί.

> **Interview gotcha:** το `==` σε **objects** συγκρίνει **references** (ίδιο αντικείμενο;), όχι τιμές. Για ισότητα τιμής χρησιμοποιείς **`.equals()`**. Κλασικό bug: `String a = ...; if (a == b)` — μπορεί να είναι false ακόμα κι αν τα κείμενα είναι ίδια· θέλεις `a.equals(b)`. (Στα primitives, `==` συγκρίνει τιμές κανονικά.)

## Το OOP mental model

Η Java είναι θεμελιωδώς **object-oriented**: οργανώνεις τον κώδικα σε **κλάσεις** (blueprints) που παράγουν **objects** (instances) με **state** (fields) και **behavior** (methods).

```java
public class Product {
    private String title;      // field (state) — private = encapsulation
    private double price;

    public Product(String title, double price) {   // constructor
        this.title = title;
        this.price = price;
    }

    public double discountedPrice(double pct) {     // method (behavior)
        return price * (1 - pct);
    }

    public String getTitle() { return title; }      // getter
}

// Χρήση:
Product p = new Product("Καφές", 3.5);   // new → φτιάχνει instance
double d = p.discountedPrice(0.1);
```

- **`new`** δημιουργεί instance (σε αντίθεση με Kotlin που δεν έχει `new`).
- **`private`** fields + **public** getters/methods = **encapsulation** (κρύβεις το εσωτερικό state).
- **`this`** αναφέρεται στο τρέχον instance.

Τα βάθη (interfaces, inheritance, polymorphism, records) στο επόμενο μάθημα.

## `null` & το NullPointerException

Σε αντίθεση με την Kotlin, η Java **δεν** έχει null safety στο type system: **οποιοδήποτε** object reference μπορεί να είναι `null`, και το `NullPointerException` (NPE) είναι το πιο κοινό runtime error. Στρατηγικές άμυνας: έλεγχοι `if (x != null)`, `Objects.requireNonNull(...)`, και το **`Optional<T>`** (θα το δεις στο Streams μάθημα) για να εκφράσεις ρητά «μπορεί να λείπει».

## Πώς απαντάς στη συνέντευξη

> «How does Java run, and what makes it platform-independent?»

> Java uses a two-stage model. The `javac` compiler turns my source into bytecode — a portable `.class` file — and the JVM executes that bytecode, JIT-compiling hot paths to native code for speed. Because every platform ships a JVM that runs the same bytecode, it's write once, run anywhere: the JVM is the abstraction over the operating system. That's also why Kotlin and Java interoperate — both compile to the same bytecode. Java is statically typed, so types are checked at compile time and mistakes are caught before running; `var` gives me local type inference without making it dynamic. One thing specific to Java is the split between primitives like `int` and `boolean`, which hold values directly and can't be null, and reference types like `Integer` and `String`, which hold references and can be null, with autoboxing converting between them. That leads to two classic gotchas I watch for: `==` on objects compares references, so I use `.equals()` for value equality, and unboxing a null wrapper into a primitive throws a NullPointerException. Unlike Kotlin, Java has no null safety in the type system, so I guard nulls explicitly or use `Optional`.
