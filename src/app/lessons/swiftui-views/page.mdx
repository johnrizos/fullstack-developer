# SwiftUI Views & Layout

Το **SwiftUI** είναι το declarative UI framework της Apple (από το 2019). Αντί να δημιουργείς και να μεταλλάσσεις UI αντικείμενα με το χέρι (το imperative μοντέλο του παλιού UIKit), **περιγράφεις** πώς πρέπει να δείχνει το UI για μια δεδομένη κατάσταση, και το framework το χτίζει και το ενημερώνει για σένα. Αν έρχεσαι από React ή Jetpack Compose, το μοντέλο θα σου φανεί οικείο: **UI = f(state)**.

Αυτό το μάθημα είναι για το **UI layer** — δομή, layout, modifiers. Το state (πώς αλλάζει το UI όταν αλλάζουν τα δεδομένα) είναι το επόμενο μάθημα.

## Τι πρέπει να μπορείς στο τέλος

- να γράφεις ένα `View` με `body` και να καταλαβαίνεις τι σημαίνει `some View`,
- να στοιβάζεις UI με `VStack`/`HStack`/`ZStack`,
- να εφαρμόζεις **modifiers** και να ξέρεις γιατί η **σειρά μετράει**,
- να χρησιμοποιείς `Text`/`Image`/`Button` και βασικά controls,
- να φτιάχνεις λίστες με `List` και `ForEach`,
- να καταλαβαίνεις το declarative μοντέλο σε αντίθεση με το imperative UIKit.

## Ένα View — δομή

Κάθε κομμάτι UI στο SwiftUI είναι ένα **`struct`** που conform-άρει στο `View` protocol και έχει μια `body` property:

```swift
import SwiftUI

struct GreetingView: View {
    let name: String

    var body: some View {
        Text("Γεια, \(name)!")
            .font(.title)
            .foregroundStyle(.blue)
    }
}
```

- Το view είναι **struct** (value type) — φθηνό, χωρίς identity. Το SwiftUI τα δημιουργεί/πετάει συνέχεια.
- Το `body` επιστρέφει `some View` — ένα **opaque type**: «κάποιος συγκεκριμένος τύπος View που δεν χρειάζεται να ονομάσω». Ο compiler ξέρει τον ακριβή τύπο· εσύ απλώς λες «είναι κάποιο View».
- Το UI **περιγράφεται declaratively**: δεν λες «φτιάξε ένα label, βάλε το κείμενο, χρωμάτισέ το» — λες «εδώ υπάρχει ένα μπλε Text».

> **Declarative vs imperative:** Στο παλιό UIKit έγραφες `let label = UILabel(); label.text = "..."; view.addSubview(label)` και μετά ενημέρωνες το `label.text` με το χέρι όταν άλλαζε κάτι. Στο SwiftUI περιγράφεις το τελικό αποτέλεσμα ως συνάρτηση της κατάστασης· όταν η κατάσταση αλλάξει, το framework ξαναϋπολογίζει το `body` και κάνει μόνο του τις ελάχιστες αλλαγές.

## Stacks — το layout πρωτεύον εργαλείο

Το SwiftUI χτίζει layout στοιβάζοντας views:

```swift
VStack(alignment: .leading, spacing: 8) {   // κάθετα
    Text("Καφές").font(.headline)
    Text("€3.50").foregroundStyle(.secondary)
}

HStack(spacing: 12) {   // οριζόντια
    Image(systemName: "cart")
    Text("Καλάθι")
}

ZStack {   // το ένα πάνω στο άλλο (βάθος)
    Color.blue
    Text("Overlay").foregroundStyle(.white)
}
```

- **`VStack`** — παιδιά το ένα κάτω από το άλλο.
- **`HStack`** — το ένα δίπλα στο άλλο.
- **`ZStack`** — το ένα πάνω στο άλλο (για overlays/badges).

Χρήσιμα layout βοηθήματα: `Spacer()` (σπρώχνει τα υπόλοιπα, «τρώει» τον ελεύθερο χώρο), `padding()`, και `alignment`/`spacing` args.

## Modifiers — και γιατί η σειρά μετράει

Ένας **modifier** επιστρέφει ένα **νέο, τυλιγμένο view** με μια αλλαγή. Τους αλυσιδώνεις:

```swift
Text("Sale")
    .padding(8)
    .background(.red)
    .foregroundStyle(.white)
    .clipShape(.capsule)
```

Επειδή κάθε modifier τυλίγει το προηγούμενο αποτέλεσμα, η **σειρά αλλάζει το αποτέλεσμα**:

```swift
// A: padding ΜΕΤΑ background → το κόκκινο περιλαμβάνει το padding (μεγάλο κόκκινο)
Text("Hi").padding().background(.red)

// B: background ΜΕΤΑ padding → βάφεται μόνο το κείμενο, μετά μπαίνει διάφανο padding γύρω
Text("Hi").background(.red).padding()
```

> Αυτό είναι το **#1 first-day gotcha** στο SwiftUI (ίδιο με τα Modifier chains στο Compose). Σκέψου κάθε modifier ως «τύλιξε το τρέχον view σε ένα καινούριο». `.frame()` πριν ή μετά το `.background()` δίνει τελείως διαφορετικό αποτέλεσμα.

## Text, Image & controls

```swift
Text("Τίτλος")
    .font(.largeTitle)
    .bold()

Image(systemName: "star.fill")   // SF Symbols — built-in εικονίδια
    .foregroundStyle(.yellow)

Button("Αγορά") {
    // action — τι γίνεται στο tap
    print("tapped")
}
.buttonStyle(.borderedProminent)

TextField("Email", text: $email)   // το $ = binding (επόμενο μάθημα)
    .textFieldStyle(.roundedBorder)
```

Τα **SF Symbols** (`Image(systemName:)`) είναι χιλιάδες έτοιμα, scalable εικονίδια που ταιριάζουν με το system font — τα χρησιμοποιείς παντού χωρίς assets.

## Λίστες — `List` & `ForEach`

Για scrollable λίστες δεδομένων:

```swift
struct Product: Identifiable {
    let id: String
    let title: String
}

struct ProductList: View {
    let products: [Product]

    var body: some View {
        List(products) { product in
            Text(product.title)
        }
    }
}
```

- Το `List` δίνει scrolling, separators και native εμφάνιση **δωρεάν**, και είναι **virtualized** (renderάρει μόνο τα ορατά cells — σαν FlatList στο RN).
- Χρειάζεται **σταθερή ταυτότητα** ανά στοιχείο. Είτε το type conform-άρει `Identifiable` (property `id`), είτε δίνεις `id:` ρητά. Χωρίς σταθερό id, το SwiftUI δεν ξέρει ποιο cell άλλαξε — ίδια ιδέα με τα React keys.

Για custom layout αντί για native rows χρησιμοποιείς `ScrollView { LazyVStack { ForEach(...) } }`.

## Reusable, συνθέσιμα views

Επειδή τα views είναι απλά structs, τα **συνθέτεις** σε μικρότερα κομμάτια — ακριβώς όπως components στο React:

```swift
struct PriceTag: View {
    let price: Double
    var body: some View {
        Text("€\(price, specifier: "%.2f")")
            .font(.caption).bold()
            .padding(6)
            .background(.green.opacity(0.2))
            .clipShape(.capsule)
    }
}

struct ProductRow: View {
    let product: Product
    var body: some View {
        HStack {
            Text(product.title)
            Spacer()
            PriceTag(price: product.price)   // reuse
        }
    }
}
```

> Κράτα τα views **μικρά**. Ένα τεράστιο `body` είναι δύσκολο να διαβαστεί και βλάπτει την επίδοση (το SwiftUI ξαναϋπολογίζει μεγαλύτερα κομμάτια). Σπάσε σε υπο-views με ξεκάθαρα ονόματα.

## Πώς απαντάς στη συνέντευξη

> «What makes SwiftUI declarative, and why does modifier order matter?»

> In SwiftUI I describe what the UI should look like for a given state rather than imperatively creating and mutating view objects like in UIKit. A view is a lightweight `struct` conforming to `View`, with a `body` that returns `some View` — an opaque type the compiler knows precisely but I don't have to spell out. I lay things out by stacking: `VStack`, `HStack`, `ZStack`. Styling happens through modifiers, and the key gotcha is that each modifier wraps the previous view and returns a new one, so order changes the result — padding before background paints a larger area than background before padding. When state changes, the framework re-evaluates `body` and applies the minimal updates, so I never manually sync the UI. For lists I use `List`/`ForEach` with stable identity via `Identifiable`, the same idea as React keys, which lets SwiftUI diff rows efficiently. And I keep views small and composed, both for readability and performance.
