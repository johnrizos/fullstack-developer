# Lists & Performance: το πιο κρίσιμο mobile skill

Οι λίστες είναι παντού στα mobile apps — feeds, chats, καλάθια, αποτελέσματα αναζήτησης. Και είναι η **#1 πηγή performance προβλημάτων**: jank στο scroll, «παγωμένο» UI, υπερβολική μνήμη. Ένα mid-range Android τηλέφωνο είναι πολύ πιο αδύναμο από το laptop σου, οπότε ό,τι «περνάει» στο web μπορεί να κολλήσει εδώ. Αυτό το μάθημα καλύπτει το virtualization με `FlatList`/`SectionList` και τα mobile-specific performance gotchas που ρωτάνε σε κάθε RN συνέντευξη.

## Τι πρέπει να μπορείς στο τέλος

- να εξηγείς **virtualization** και γιατί το χρειάζεσαι,
- να χρησιμοποιείς `FlatList`/`SectionList` σωστά (`keyExtractor`, `renderItem`),
- να αποφεύγεις τα κλασικά λάθη που σκοτώνουν την απόδοση,
- να ξέρεις πότε φεύγεις σε `FlashList`,
- να κατανοείς JS thread vs UI thread και γιατί κολλάει το scroll,
- να βελτιστοποιείς με `memo`, σταθερές references, `getItemLayout`.

## Virtualization — η βασική ιδέα

Αν έχεις 10.000 items και τα renderάρεις όλα (`ScrollView` + `.map()`), φτιάχνεις 10.000 native views ταυτόχρονα: τεράστια μνήμη, αργό mount, jank. **Virtualization** σημαίνει: renderάρω μόνο ό,τι φαίνεται στην οθόνη (+ ένα μικρό buffer πάνω/κάτω), και καθώς κάνεις scroll **ανακυκλώνω** views για τα νέα items. Ανεξάρτητα αν η λίστα έχει 100 ή 100.000 items, στη μνήμη μένουν λίγες δεκάδες.

Το `FlatList` (και το `SectionList` για grouped δεδομένα) το κάνει αυτό αυτόματα. Γι' αυτό: **ποτέ** μεγάλη λίστα σε `ScrollView`.

## `FlatList` — σωστή χρήση

```tsx
<FlatList
  data={products}
  keyExtractor={(item) => item.id}
  renderItem={({ item }) => <ProductRow product={item} />}
  ListEmptyComponent={<EmptyState />}
  ListHeaderComponent={<SearchBar />}
  onEndReached={loadMore}
  onEndReachedThreshold={0.5}
  refreshing={isRefreshing}
  onRefresh={refetch}
/>
```

Τα βασικά props:
- **`data`** — ο πίνακας.
- **`renderItem`** — πώς φτιάχνεται μια γραμμή (παίρνει `{ item, index }`).
- **`keyExtractor`** — σταθερό, μοναδικό key ανά item (σαν το `key` στο web· κρίσιμο για σωστό recycling).
- **`onEndReached`** + **`onEndReachedThreshold`** — infinite scroll / pagination.
- **`onRefresh`** + **`refreshing`** — pull-to-refresh (native gesture).
- **`ListHeaderComponent` / `ListFooterComponent` / `ListEmptyComponent`** — αντί να τα φτιάχνεις έξω.
- **`ItemSeparatorComponent`** — διαχωριστικά μεταξύ γραμμών.

## `SectionList` — grouped δεδομένα

Για λίστες με **sections & headers** (π.χ. επαφές ανά αρχικό γράμμα, μηνύματα ανά ημέρα):

```tsx
<SectionList
  sections={[
    { title: "A", data: contactsA },
    { title: "B", data: contactsB },
  ]}
  keyExtractor={(item) => item.id}
  renderItem={({ item }) => <ContactRow contact={item} />}
  renderSectionHeader={({ section }) => <SectionHeader title={section.title} />}
  stickySectionHeadersEnabled
/>
```

## Τα λάθη που σκοτώνουν την απόδοση

**1. Inline functions & objects στο `renderItem`.** Κάθε render φτιάχνει νέα reference → κάθε row ξανα-renderάρει.

```tsx
// ❌ νέα function κάθε render → σπάει το memo του row
renderItem={({ item }) => <Row onPress={() => open(item.id)} style={{ padding: 8 }} />}

// ✅ memoized row + σταθερό style (StyleSheet) + σταθερός handler
const Row = memo(function Row({ item, onPress }) { /* ... */ });
```

**2. Μη-memoized row component.** Τύλιξε το row σε `React.memo` ώστε να μην ξανα-renderάρει όταν δεν άλλαξαν τα props του. (Ισχύουν τα ίδια όπως στο web React performance μάθημα — reference equality.)

**3. Ασταθές `keyExtractor` (π.χ. `index`).** Αν χρησιμοποιήσεις index ως key και η λίστα αλλάξει σειρά/φιλτραριστεί, το recycling μπερδεύεται — λάθος περιεχόμενο σε λάθος γραμμή. Χρησιμοποίησε σταθερό id.

**4. Βαριά items.** Μεγάλες μη-βελτιστοποιημένες εικόνες, βαθιά nested views, sync υπολογισμοί μέσα στο `renderItem`. Κράτα το row ελαφρύ.

**5. `getItemLayout` για σταθερά ύψη.** Αν όλες οι γραμμές έχουν **ίδιο, γνωστό ύψος**, δώσε `getItemLayout` — το FlatList δεν χρειάζεται να μετρήσει, οπότε το scroll & το scroll-to-index γίνονται στιγμιαία.

## JS thread vs UI thread — γιατί κολλάει το scroll

Θυμήσου από τα foundations: ο JS σου τρέχει σε **ένα JS thread**. Το scrolling/gestures χειρίζεται (στη νέα αρχιτεκτονική) το native UI thread, αλλά το **`renderItem` και τα state updates τρέχουν στο JS thread**. Αν φορτώσεις το JS thread (βαρύ render, μεγάλα state updates, JSON parsing), το thread δεν προλαβαίνει → **dropped frames** → jank.

Πρακτικά:
- Κράτα τα rows ελαφριά και memoized.
- Κάνε βαριά δουλειά (parsing, sorting) **εκτός** render, ιδανικά μια φορά.
- Για animations που πρέπει να είναι στα 60fps ενώ γίνεται δουλειά, χρησιμοποίησε **Reanimated** (τρέχει animations στο UI thread, όχι στο JS thread).

## `FlashList` — όταν το FlatList δεν φτάνει

Το **FlashList** (από τη Shopify) είναι drop-in πιο γρήγορη λίστα: πιο αποδοτικό recycling, λιγότερα blank cells σε γρήγορο scroll. Το διαλέγεις για **πολύ μεγάλες ή σύνθετες** λίστες όπου το FlatList αφήνει κενά ή κολλάει. Χρειάζεται `estimatedItemSize`. Κανόνας: ξεκίνα με FlatList· πήγαινε σε FlashList αν μετρήσεις πρόβλημα.

## Πώς απαντάς στη συνέντευξη

> «How do you build a performant list in React Native?»

> The core idea is virtualization: never put a large list in a ScrollView with map, because that mounts every native view at once and blows up memory. FlatList — or SectionList for grouped data — renders only what's on screen plus a small buffer and recycles views as you scroll, so memory stays flat whether it's a hundred or a hundred thousand items. I give it a stable keyExtractor using a real id, not the index, so recycling doesn't put the wrong content in a row. Then I keep rows cheap: wrap the row in React.memo and avoid inline functions and objects in renderItem, since a new reference every render breaks the memo and re-renders every row. If rows are a fixed known height I add getItemLayout so it skips measurement and scroll-to-index is instant. I remember my JS runs on one thread, so heavy work in renderItem drops frames — I move parsing and sorting out of render and use Reanimated for animations so they run on the UI thread. If FlatList still leaves blank cells on fast scroll I switch to FlashList. And I actually measure with the Perf Monitor on a real mid-range Android, not just the iOS simulator.
