# Spring Boot Foundations

Η Java από μόνη της είναι η γλώσσα· το **Spring** είναι ο λόγος που η Java κυριαρχεί στο enterprise backend. Το **Spring Framework** παρέχει dependency injection, web MVC, data access, security — και το **Spring Boot** το κάνει όλο εύκολο: **auto-configuration**, **starters**, embedded server, ώστε να τρέχεις production app με ελάχιστο setup. Αν έχεις δει NestJS (που εμπνεύστηκε από το Spring), το mental model θα σου φανεί οικείο.

Το πιο σημαντικό concept που πρέπει να «κουμπώσει»: το **IoC container** και το **dependency injection**. Όλα τα υπόλοιπα του Spring χτίζονται πάνω σε αυτό.

## Τι πρέπει να μπορείς στο τέλος

- να εξηγείς **Inversion of Control (IoC)** και **dependency injection**,
- να καταλαβαίνεις τι είναι ένα **bean** και το **application context**,
- να χρησιμοποιείς `@Component`/`@Service`/`@Repository` & constructor injection,
- να εξηγείς τι κάνει το **Spring Boot auto-configuration** και τα **starters**,
- να ρυθμίζεις με `application.properties`/`application.yml`,
- να διακρίνεις Spring Framework vs Spring Boot.

## Inversion of Control & Dependency Injection

Το κεντρικό concept. Κανονικά, μια κλάση **φτιάχνει** τα dependencies της:

```java
// Χωρίς DI — η κλάση ελέγχει τη δημιουργία (tight coupling)
public class OrderService {
    private final PaymentProcessor processor = new StripeProcessor();  // hardcoded
}
```

Με **Inversion of Control**, αντιστρέφεις αυτόν τον έλεγχο: δεν φτιάχνει η κλάση τα dependencies — της τα **δίνει** ένα εξωτερικό σύστημα (το Spring **container**). Το πώς γίνεται λέγεται **dependency injection**:

```java
// Με DI — τα dependencies δίνονται (loose coupling)
@Service
public class OrderService {
    private final PaymentProcessor processor;

    public OrderService(PaymentProcessor processor) {   // constructor injection
        this.processor = processor;                     // το Spring το παρέχει
    }
}
```

> **Το «γιατί»:** loose coupling → μπορείς να βάλεις **fake** processor στα tests, να αλλάξεις υλοποίηση χωρίς να πειράξεις το `OrderService`, και το Spring διαχειρίζεται **ένα** shared instance. Είναι το ίδιο DI concept που είδες σε NestJS και στο Hilt (Android) — εδώ το κάνει το Spring container. **Constructor injection** (τα dependencies στον constructor) είναι το προτεινόμενο, γιατί κάνει τα dependencies ρητά & τα fields `final`.

## Beans & το Application Context

Ένα **bean** είναι απλώς ένα αντικείμενο που **διαχειρίζεται το Spring** — το δημιουργεί, το κρατά, και το «injectάρει» όπου χρειάζεται. Το **Application Context** (ο IoC container) είναι το registry όλων των beans.

Δηλώνεις μια κλάση ως bean με stereotype annotations:

| Annotation | Σημασιολογία |
|---|---|
| `@Component` | γενικό bean |
| `@Service` | business logic layer |
| `@Repository` | data access layer (+ exception translation) |
| `@Controller` / `@RestController` | web layer |

```java
@Service
public class ProductService {
    private final ProductRepository repo;
    public ProductService(ProductRepository repo) { this.repo = repo; }
    // ...
}
```

Στο startup, το Spring **σαρώνει** (component scan) το package σου, βρίσκει όλες τις annotated κλάσεις, τις φτιάχνει ως beans, και **συνδέει** τα dependencies τους αυτόματα (autowiring). Δεν γράφεις `new ProductService(...)` πουθενά — το κάνει το container.

> Ένα `@Bean` που δηλώνεται σε `@Configuration` κλάση είναι ο εναλλακτικός τρόπος (για third-party κλάσεις που δεν μπορείς να annotate-άρεις). By default τα beans είναι **singletons** — ένα instance ανά container.

## Spring Boot: auto-configuration & starters

Το σκέτο Spring απαιτούσε **τόνους** XML/Java configuration. Το **Spring Boot** το λύνει με δύο ιδέες:

**1. Starters** — ένα dependency που φέρνει ό,τι χρειάζεσαι για μια δυνατότητα:

```
spring-boot-starter-web         → web MVC + embedded Tomcat + JSON
spring-boot-starter-data-jpa    → JPA + Hibernate + connection pool
spring-boot-starter-security    → authentication/authorization
spring-boot-starter-test        → JUnit + Mockito + Spring test
```

Αντί να διαλέγεις χειροκίνητα 15 συμβατές βιβλιοθήκες, βάζεις **έναν** starter.

**2. Auto-configuration** — το Boot κοιτάζει τι βρίσκεται στο classpath και **ρυθμίζει λογικά defaults** αυτόματα. Βρίσκει το JPA starter → στήνει DataSource/EntityManager. Βρίσκει το web starter → σηκώνει embedded Tomcat στη θύρα 8080.

```java
@SpringBootApplication   // = @Configuration + @EnableAutoConfiguration + @ComponentScan
public class ShopApplication {
    public static void main(String[] args) {
        SpringApplication.run(ShopApplication.class, args);   // σηκώνει τα πάντα
    }
}
```

> **«Convention over configuration»:** το Boot υποθέτει λογικά defaults ώστε να μη ρυθμίζεις τα πάντα· τα override-άρεις μόνο όπου χρειάζεται. Ο **embedded server** (Tomcat μέσα στο app) σημαίνει ότι τρέχεις ένα απλό `java -jar app.jar` — δεν στήνεις ξεχωριστό application server. Αυτό το «απλώς τρέχει» είναι ο λόγος επικράτησης του Boot.

## Configuration: `application.properties`

Ρυθμίσεις (DB URL, ports, keys) πάνε **έξω** από τον κώδικα, σε `application.properties` ή `application.yml`:

```properties
server.port=8080
spring.datasource.url=jdbc:postgresql://localhost:5432/shop
spring.jpa.hibernate.ddl-auto=validate
app.feature.new-checkout=true
```

Τις διαβάζεις με `@Value("${app.feature.new-checkout}")` ή, καλύτερα, με type-safe `@ConfigurationProperties` classes. Διαφορετικά **profiles** (`application-dev.properties`, `application-prod.properties`) δίνουν διαφορετικές ρυθμίσεις ανά περιβάλλον — θα το δεις στο production μάθημα.

## Πώς απαντάς στη συνέντευξη

> «Explain dependency injection in Spring and what Spring Boot adds.»

> The heart of Spring is the IoC container. Normally a class creates its own dependencies with `new`, which is tight coupling; with Inversion of Control I hand that responsibility to the Spring container, and dependency injection is how it supplies them. I annotate my classes — `@Service`, `@Repository`, `@Component` — so the container registers them as beans, and at startup component scanning finds them, instantiates them as singletons, and autowires their dependencies. I prefer constructor injection because it makes dependencies explicit and lets me mark the fields `final`, and it means I can drop in a fake in tests. The payoff is loose coupling, testability, and shared instances managed for me. Spring Boot builds on that framework with two things: starters, where a single dependency like `spring-boot-starter-web` pulls in a compatible set of libraries and an embedded Tomcat, and auto-configuration, where Boot inspects the classpath and wires sensible defaults automatically — convention over configuration. So I annotate a class with `@SpringBootApplication`, run one `main`, and get a working server on port 8080 without XML or boilerplate. Configuration like the database URL lives outside the code in `application.properties`, with profiles per environment.
