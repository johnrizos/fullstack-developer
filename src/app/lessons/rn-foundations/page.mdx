# React Native Foundations

Ξέρεις ήδη React. Το **React Native** σου δίνει να χτίσεις **πραγματικά native apps** για iOS και Android με τα ίδια εργαλεία — components, JSX, hooks, props, state. Η μεγάλη διαφορά: δεν renderάρεις σε DOM. Δεν υπάρχει `<div>`, δεν υπάρχει CSS αρχείο, δεν υπάρχει browser. Αυτό το μάθημα είναι το mental shift από web σε mobile — τι κρατάς, τι πετάς, και πώς πραγματικά τρέχει ο κώδικάς σου σε ένα κινητό.

## Τι πρέπει να μπορείς στο τέλος

- να εξηγείς τι είναι το React Native και πώς διαφέρει από web React,
- να καταλαβαίνεις πώς ο JS κώδικάς σου ελέγχει **native** UI (το bridge/JSI),
- να διαλέγεις **Expo** vs **bare** workflow και να ξέρεις γιατί,
- να ξέρεις τι μεταφέρεται από τη γνώση σου σε React και τι όχι,
- να στήνεις νοερά ένα RN project και να τρέχεις σε συσκευή/emulator.

## Τι είναι (και τι ΔΕΝ είναι) το React Native

Το React Native **δεν** είναι μια ιστοσελίδα μέσα σε app (αυτό είναι WebView / Cordova). Ούτε «μεταγλωττίζει» JavaScript σε Swift/Kotlin.

Αντ' αυτού: γράφεις components σε JavaScript/TypeScript, και το RN τα αντιστοιχίζει σε **πραγματικά native widgets** της πλατφόρμας. Ένα `<View>` γίνεται `UIView` στο iOS και `android.view.ViewGroup` στο Android. Ένα `<Text>` γίνεται `UILabel` / `TextView`. Ο χρήστης βλέπει native κουμπιά, native scrolling, native πληκτρολόγιο — όχι HTML.

> Το mental model: **γράφεις React· η React Native ζωγραφίζει native.** Ο ίδιος declarative τρόπος (UI = f(state)), αλλά ο «renderer» δεν είναι ο browser — είναι το iOS/Android.

## Πώς τρέχει πραγματικά: JS thread + native, με μια γέφυρα

Μια RN εφαρμογή τρέχει τον JavaScript σου σε ένα **JS engine** (σήμερα το **Hermes**, φτιαγμένο από τη Meta) σε ξεχωριστό thread. Το native UI ζει σε άλλο thread (το UI/main thread). Οι δύο κόσμοι επικοινωνούν:

- **Παλιό μοντέλο (bridge):** JS και native έστελναν ασύγχρονα **serialized JSON μηνύματα** μέσα από μια γέφυρα. Λειτουργικό, αλλά το πέρασμα μηνυμάτων μπορούσε να γίνει bottleneck (π.χ. σε γρήγορο scrolling/animations).
- **Νέα αρχιτεκτονική (JSI + Fabric + TurboModules):** το JS καλεί **απευθείας** C++ αναφορές σε native αντικείμενα, σύγχρονα όπου χρειάζεται, χωρίς JSON serialization. Πιο γρήγορο, λιγότερο lag.

Γιατί σε νοιάζει; Επειδή εξηγεί δύο πράγματα: (1) γιατί βαριοί υπολογισμοί στο JS thread «κολλάνε» το UI, και (2) γιατί κάποια features χρειάζονται **native module** — κώδικα στη native πλατφόρμα που εκθέτει λειτουργικότητα στο JS.

## Τι κρατάς από τη React γνώση σου

Σχεδόν όλο το μοντέλο μεταφέρεται:

| Ίδιο με web React | Διαφορετικό στο RN |
|---|---|
| Components, JSX, props, `children` | Χωρίς DOM: `<View>` αντί `<div>`, `<Text>` αντί `<p>` |
| `useState`, `useEffect`, custom hooks | Χωρίς CSS files: styling με JS objects (`StyleSheet`) |
| One-way data flow, composition | Χωρίς `<a href>`: navigation με βιβλιοθήκη (React Navigation) |
| Reconciliation, keys, re-renders | Χωρίς `className`: `style={styles.x}` |
| Context, reducers, state management | Events: `onPress` αντί `onClick`· δεν υπάρχει hover |

Το κρίσιμο σημείο για συνέντευξη: **το component/hooks μοντέλο είναι ταυτόσημο**· αλλάζει το **primitive vocabulary** (τα building blocks) και το **styling/layout** (όλα Flexbox σε JS).

## Expo vs bare — ποιο workflow

Δύο τρόποι να ξεκινήσεις ένα RN project:

- **Expo (managed):** ένα framework/toolchain πάνω από το RN. Σου δίνει έτοιμο build system, over-the-air updates, ένα τεράστιο σετ από native APIs (camera, location, notifications) χωρίς να αγγίξεις Xcode/Android Studio, και το **Expo Go** app για instant preview στο τηλέφωνό σου. Σήμερα ο **προτεινόμενος** τρόπος για τους περισσότερους — και το ίδιο το RN documentation προτείνει framework (Expo) αντί για σκέτο RN.
- **Bare / prebuild:** έχεις πλήρη πρόσβαση στα native `ios/` και `android/` folders. Το διαλέγεις όταν χρειάζεσαι custom native code που δεν καλύπτεται, ή πολύ ειδικά native builds. Το Expo πλέον υποστηρίζει **config plugins** και **prebuild** ώστε να προσθέτεις native modules χωρίς να «βγεις» εντελώς από το managed workflow.

> Πρακτικός κανόνας: **ξεκίνα με Expo.** «Βγαίνεις» (prebuild/eject) μόνο όταν σε μπλοκάρει συγκεκριμένη native ανάγκη — όχι προληπτικά.

## Πώς μοιάζει το πρώτο σου component

```tsx
import { View, Text, StyleSheet } from "react-native";

export default function App() {
  return (
    <View style={styles.container}>
      <Text style={styles.title}>Γεια σου Mobile 👋</Text>
    </View>
  );
}

const styles = StyleSheet.create({
  container: { flex: 1, justifyContent: "center", alignItems: "center" },
  title: { fontSize: 24, fontWeight: "600" },
});
```

Δες τι λείπει σε σχέση με web: κανένα `<div>`, κανένα `className`, κανένα `.css`. Κάθε κείμενο **πρέπει** να μπει μέσα σε `<Text>` (δεν βάζεις γυμνό string μέσα σε `<View>`). Το layout είναι Flexbox — και το `flex: 1` σημαίνει «γέμισε τον διαθέσιμο χώρο».

## Development loop

- **Metro** είναι ο JS bundler του RN (ανάλογο του Vite/webpack για web).
- **Fast Refresh** κρατά το state σου ενώ αλλάζεις κώδικα — σαν HMR στο web.
- Τρέχεις σε **iOS Simulator** (μόνο macOS), **Android Emulator**, ή σε **πραγματική συσκευή** μέσω Expo Go / dev build. Δοκίμασε πάντα σε πραγματική συσκευή πριν το release — performance και gestures διαφέρουν από τον emulator.

## Πώς απαντάς στη συνέντευξη

> «What is React Native and how does it differ from React on the web?»

> React Native lets me build genuinely native iOS and Android apps using the same React model — components, JSX, hooks, props, one-way data flow. The difference is the render target: there's no DOM. Instead of divs and CSS, I compose native primitives like View and Text, and my JavaScript controls real native widgets — a View becomes a UIView on iOS and a ViewGroup on Android. My JS runs on a JS engine, Hermes, on its own thread, and talks to the native UI thread. The old architecture passed serialized JSON across a bridge asynchronously, which could bottleneck; the new architecture — JSI with Fabric and TurboModules — calls native directly from JS through C++ references, so it's faster and more synchronous. Practically, the component and hooks model transfers one-to-one; what changes is the primitive vocabulary, styling which is all Flexbox in JS objects, and navigation which needs a library. For most projects I'd start with Expo — it gives me the build system, OTA updates, and a huge set of native APIs without touching Xcode — and only go bare when a specific native need forces it.
