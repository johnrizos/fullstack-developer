# State & Data Flow

Στο προηγούμενο μάθημα το UI ήταν **στατικό**. Τώρα το κάνουμε ζωντανό. Το SwiftUI, όπως το React και το Compose, στηρίζεται στην αρχή **UI = f(state)**: δεν αλλάζεις το UI με το χέρι — αλλάζεις την **κατάσταση**, και το framework ξαναϋπολογίζει τα views που εξαρτώνται από αυτήν. Το κλειδί είναι να ξέρεις **ποιος κατέχει** κάθε κομμάτι κατάστασης και **πώς ρέει** προς τα views.

Θα δούμε τα property wrappers που ορίζουν αυτό το μοντέλο: `@State`, `@Binding`, το σύγχρονο `@Observable` (Observation framework, iOS 17+) και `@Environment`.

## Τι πρέπει να μπορείς στο τέλος

- να καταλαβαίνεις το declarative state model (`UI = f(state)`),
- να κατέχεις τοπική κατάσταση view με `@State`,
- να μοιράζεσαι mutable κατάσταση προς τα κάτω με `@Binding` (state hoisting),
- να μοντελοποιείς πιο σύνθετη κατάσταση με `@Observable` κλάσεις,
- να διαχέεις shared κατάσταση χωρίς prop-drilling με `@Environment`,
- να ξέρεις πού πρέπει να «ζει» κάθε κατάσταση (single source of truth).

## Το declarative state model

Στο SwiftUI **δεν** γράφεις «όταν αλλάξει το x, ενημέρωσε το label». Δηλώνεις ότι το label **παράγεται** από το x. Όταν το x αλλάξει, το SwiftUI ξανατρέχει το `body` και ενημερώνει μόνο ό,τι χρειάζεται:

```swift
struct CounterView: View {
    @State private var count = 0

    var body: some View {
        VStack {
            Text("Μετρητής: \(count)")   // παράγεται από το count
            Button("Αύξηση") { count += 1 }   // αλλάζει το state
        }
    }
}
```

Πατάς το κουμπί → αλλάζει το `count` → το SwiftUI ξαναϋπολογίζει το `body` → το `Text` δείχνει τη νέα τιμή. **Ποτέ** δεν αγγίζεις το `Text` άμεσα.

## `@State` — τοπική κατάσταση ενός view

Το `@State` δηλώνει ότι ένα view **κατέχει** ένα κομμάτι mutable κατάστασης. Επειδή τα views είναι structs (πετιούνται & ξαναφτιάχνονται συνέχεια), το SwiftUI αποθηκεύει την πραγματική τιμή **έξω** από το struct και τη διατηρεί ανάμεσα στα re-renders. Όταν αλλάζει, ενεργοποιεί re-render.

```swift
@State private var isOn = false
@State private var text = ""
```

> Κανόνες: το `@State` είναι **`private`** (ανήκει σε αυτό το view, κανείς άλλος) και για **απλή, τοπική** κατάσταση (toggle, τιμή ενός field, ποιο tab είναι επιλεγμένο). Για κατάσταση που μοιράζεται ή έχει λογική, θα δούμε `@Observable` παρακάτω.

## `@Binding` — state hoisting προς τα κάτω

Τι γίνεται όταν ένα **child** view πρέπει να **διαβάζει και να γράφει** κατάσταση που κατέχει ο **parent**; Δεν αντιγράφεις την τιμή (θα ξεσυγχρονιστεί). Περνάς **`@Binding`** — μια αναφορά two-way στην πηγή:

```swift
struct ToggleRow: View {
    let label: String
    @Binding var isOn: Bool   // δεν κατέχει την τιμή — δείχνει στην πηγή

    var body: some View {
        Toggle(label, isOn: $isOn)
    }
}

struct SettingsView: View {
    @State private var notifications = true   // ο parent ΚΑΤΕΧΕΙ την τιμή

    var body: some View {
        ToggleRow(label: "Ειδοποιήσεις", isOn: $notifications)
        //                                       ↑ το $ φτιάχνει binding στο @State
    }
}
```

- Το **`$`** μπροστά από ένα `@State`/`@Observable` property δίνει το **binding** (την two-way αναφορά).
- Ο parent είναι ο **single source of truth**· το child απλώς διαβάζει/γράφει μέσω binding.
- Αυτό είναι **state hoisting** + **unidirectional data flow**: η κατάσταση ζει ψηλά, τα events ρέουν πάνω, τα δεδομένα ρέουν κάτω — ίδια αρχή με React/Compose.

## `@Observable` — reference-type κατάσταση με λογική

Για κατάσταση με πολλά πεδία και λογική (ένα view model, ένα cart, ένα session) φτιάχνεις **class** με το macro **`@Observable`** (Observation framework, iOS 17+, αντικατέστησε το παλιό `ObservableObject`/`@Published`):

```swift
import Observation

@Observable
final class CartModel {
    var items: [Product] = []
    var isLoading = false

    var total: Double { items.reduce(0) { $0 + $1.price } }   // computed

    func add(_ p: Product) { items.append(p) }
}
```

Το χρησιμοποιείς σε ένα view. Το SwiftUI **παρακολουθεί αυτόματα** ποια πεδία διαβάζει το `body` και ξανα-renderάρει **μόνο** όταν αλλάξει ένα πεδίο που όντως χρησιμοποιείς:

```swift
struct CartView: View {
    @State private var cart = CartModel()   // το view κατέχει το model

    var body: some View {
        VStack {
            Text("Σύνολο: €\(cart.total, specifier: "%.2f")")
            List(cart.items) { Text($0.title) }
        }
    }
}
```

> **Γιατί @Observable αντί για ObservableObject:** το νέο Observation framework κάνει **fine-grained tracking** — το view ξανα-renderάρει μόνο για τα πεδία που διαβάζει, όχι για κάθε αλλαγή του object. Λιγότερα περιττά re-renders, λιγότερο boilerplate (κανένα `@Published` σε κάθε property).

## Πώς διαλέγεις wrapper όταν κρατάς ένα model

- **`@State private var model = FooModel()`** — αυτό το view **δημιουργεί & κατέχει** το model.
- **`@Bindable var model: FooModel`** — έχεις ήδη ένα `@Observable` model και θέλεις να φτιάξεις **bindings** στα πεδία του (`$model.name` σε ένα TextField).
- Απλό pass-down χωρίς binding: απλώς περνάς το `model` ως κανονικό property.

## `@Environment` — shared κατάσταση χωρίς prop-drilling

Όταν πολλά, βαθιά views χρειάζονται το **ίδιο** πράγμα (theme, auth session, ρυθμίσεις), το να το περνάς χειροκίνητα σε κάθε επίπεδο είναι **prop-drilling**. Το `@Environment` το διαχέει στο δέντρο — όποιο view το χρειάζεται, το ζητά:

```swift
@Observable class Session { var user: User? }

// Στη ρίζα:
ContentView()
    .environment(session)

// Οποιοδήποτε βαθύ view:
struct ProfileButton: View {
    @Environment(Session.self) private var session
    var body: some View {
        Text(session.user?.name ?? "Guest")
    }
}
```

Το SwiftUI έχει και built-in environment values: `@Environment(\.colorScheme)` (light/dark), `@Environment(\.dismiss)` (κλείσε το τρέχον screen), κ.ά.

## Single source of truth — πού ζει κάθε κατάσταση;

Ο πιο συχνός λόγος για UI bugs είναι **διπλή κατάσταση** που ξεσυγχρονίζεται. Ο κανόνας:

- Κάθε κομμάτι κατάστασης έχει **έναν** ιδιοκτήτη (single source of truth).
- Τοπικό & απλό → `@State` σε αυτό το view.
- Πρέπει child να το γράφει → κράτα το στον parent, πέρασε `@Binding`.
- Μοιράζεται από πολλά, με λογική → `@Observable` model (και `@Environment` αν είναι πολύ διάχυτο).
- **Μην** αντιγράφεις κατάσταση σε πολλά views· παρήγαγε ό,τι χρειάζεσαι με computed properties.

## Πώς απαντάς στη συνέντευξη

> «How does state and data flow work in SwiftUI?»

> SwiftUI is declarative: the UI is a function of state. I never mutate views directly — I change state, and the framework re-evaluates the affected `body`. For a view's own simple, local state I use `@State`, kept private because the view owns it. When a child needs to read and write state the parent owns, I hoist the state up and pass a `@Binding` with the `$` prefix, so the parent stays the single source of truth and data flows one way — events up, data down. For richer state with logic I model it as an `@Observable` class from the Observation framework; SwiftUI tracks exactly which properties a view reads and only re-renders for those, which is finer-grained and less boilerplate than the old `ObservableObject`/`@Published`. And when many deep views need the same thing — a session or theme — I put it in the `@Environment` instead of prop-drilling. The rule underneath all of it is single source of truth: every piece of state has exactly one owner, and I derive everything else with computed properties.
