# State & ViewModel

Στο προηγούμενο μάθημα είδες ότι **UI = f(state)** — το Compose ζωγραφίζει με βάση το state. Αλλά **πού ζει** αυτό το state, **πώς αλλάζει**, και **πώς επιβιώνει** ένα rotation της οθόνης; Αυτό είναι το πιο κρίσιμο μάθημα του Compose. Θα δεις `remember`/`mutableStateOf`, το πρότυπο **state hoisting**, το **unidirectional data flow**, και το **ViewModel** που κρατά state πέρα από τον κύκλο ζωής του UI.

Αν ξέρεις React: `remember { mutableStateOf() }` ≈ `useState`, `LaunchedEffect` ≈ `useEffect`, το ViewModel παίζει τον ρόλο ενός store/hook που ζει έξω από το render.

## Τι πρέπει να μπορείς στο τέλος

- να δημιουργείς state με `remember { mutableStateOf(...) }` και να ξέρεις τι κάνει το καθένα,
- να εφαρμόζεις **state hoisting** και **unidirectional data flow** (state κάτω, events πάνω),
- να διατηρείς state σε configuration changes με `rememberSaveable` και `ViewModel`,
- να εκθέτεις UI state από ViewModel ως `StateFlow` και να το διαβάζεις με `collectAsStateWithLifecycle`,
- να τρέχεις side-effects σωστά με `LaunchedEffect`.

## `remember` + `mutableStateOf`

Δύο ξεχωριστά πράγματα που σχεδόν πάντα πάνε μαζί:

```kotlin
@Composable
fun Counter() {
    var count by remember { mutableStateOf(0) }

    Button(onClick = { count++ }) {
        Text("Πατήθηκε $count φορές")
    }
}
```

- **`mutableStateOf(0)`** φτιάχνει ένα **observable** state holder. Όταν η `.value` του αλλάξει, το Compose κάνει **recompose** όποιο composable το διαβάζει.
- **`remember { }`** λέει «κράτα αυτή την τιμή **ανάμεσα σε recompositions**». Χωρίς `remember`, κάθε recomposition θα ξανάφτιαχνε το state από την αρχή (0) — και ποτέ δεν θα μετρούσε.
- Το **`by`** (property delegate) σε αφήνει να γράφεις `count` αντί `count.value`.

> Το ζευγάρι: `mutableStateOf` = «κάν' το observable ώστε το UI να αντιδρά», `remember` = «μη το ξαναφτιάχνεις σε κάθε recompose». Χρειάζεσαι **και** τα δύο. Παράλληλο με React: `mutableStateOf` ≈ το reactive κομμάτι του `useState`, `remember` ≈ ότι το `useState` επιβιώνει μεταξύ renders.

## State hoisting & unidirectional data flow

Ένα καλό composable είναι **stateless** όσο γίνεται: δέχεται την τιμή ως παράμετρο και «ανεβάζει» (hoists) το state στον γονιό, ειδοποιώντας τον για αλλαγές μέσω callback. Αυτό είναι **state hoisting**:

```kotlin
// Stateless — reusable, testable, "controlled"
@Composable
fun SearchBar(query: String, onQueryChange: (String) -> Unit) {
    OutlinedTextField(value = query, onValueChange = onQueryChange)
}

// Ο γονιός κρατά το state (stateful)
@Composable
fun SearchScreen() {
    var query by remember { mutableStateOf("") }
    SearchBar(query = query, onQueryChange = { query = it })
}
```

Το μοτίβο λέγεται **unidirectional data flow (UDF)**:

- **State ρέει προς τα κάτω** (parent → child ως παράμετρος).
- **Events ρέουν προς τα πάνω** (child → parent ως callback: `onQueryChange`).

> Ίδια αρχή με React «controlled components» (`value` + `onChange`). Οφέλη: το child είναι reusable & εύκολα testable (δεν κρατά κρυφό state), και υπάρχει **μία** πηγή αλήθειας. Ο κανόνας: σήκωσε το state **ακριβώς όσο ψηλά** χρειάζεται να το μοιραστούν/ελεγχθούν — όχι πιο ψηλά.

## Το πρόβλημα: configuration changes

Όταν ο χρήστης **γυρίζει** τη συσκευή (portrait↔landscape), το Android **καταστρέφει και ξαναφτιάχνει** το Activity. Ό,τι state ήταν σε `remember` **χάνεται** (το composition ξαναστήνεται). Δύο εργαλεία:

```kotlin
// rememberSaveable: επιβιώνει configuration changes (σώζεται σε Bundle)
var query by rememberSaveable { mutableStateOf("") }
```

Το `rememberSaveable` καλύπτει απλά, serializable UI state (κείμενο ενός πεδίου, ποιο tab). Αλλά για **πραγματικό app state** (φορτωμένα δεδομένα, business logic) η σωστή λύση είναι το **ViewModel**.

## `ViewModel` — state πέρα από το UI lifecycle

Ένα **`ViewModel`** είναι μια κλάση που **επιβιώνει configuration changes**: ζει όσο η οθόνη λογικά υπάρχει (ακόμα κι αν το Activity ξαναφτιαχτεί), και καθαρίζεται μόνο όταν ο χρήστης φύγει οριστικά. Κρατά το UI state και το business logic **έξω** από τα composables.

```kotlin
class SearchViewModel : ViewModel() {
    private val _state = MutableStateFlow(SearchUiState())
    val state: StateFlow<SearchUiState> = _state.asStateFlow()

    fun onQueryChange(q: String) {
        _state.update { it.copy(query = q) }
    }

    fun search() {
        viewModelScope.launch {
            _state.update { it.copy(loading = true) }
            val results = repo.search(_state.value.query)
            _state.update { it.copy(loading = false, results = results) }
        }
    }
}

data class SearchUiState(
    val query: String = "",
    val loading: Boolean = false,
    val results: List<Product> = emptyList(),
)
```

Στο composable, παίρνεις το ViewModel και **collect**-άρεις το state:

```kotlin
@Composable
fun SearchScreen(vm: SearchViewModel = viewModel()) {
    val state by vm.state.collectAsStateWithLifecycle()

    SearchBar(query = state.query, onQueryChange = vm::onQueryChange)
    if (state.loading) CircularProgressIndicator()
    LazyColumn {
        items(state.results) { ProductRow(it) }
    }
}
```

- `viewModel()` δίνει το (ίδιο) ViewModel instance που επιβιώνει το rotation.
- `collectAsStateWithLifecycle()` μετατρέπει το `StateFlow` σε Compose state **και** σταματά να συλλέγει όταν η οθόνη πάει background (εξοικονομεί πόρους) — προτιμάται από το σκέτο `collectAsState()`.
- Ένα **`data class` UI state** (single object) αντί για πολλά ξεχωριστά flows κρατά την οθόνη συνεπή· τα updates γίνονται immutable με `copy()`.

> Ο διαχωρισμός: **ViewModel** = state + logic (survives rotation, testable χωρίς UI). **Composable** = μόνο rendering + προώθηση events. Το UDF συνεχίζεται: state ρέει από το ViewModel στο UI, events (`vm::onQueryChange`) πάνε από το UI στο ViewModel.

## Side-effects: `LaunchedEffect`

Δεν κάνεις side-effects (network call, analytics) στο **σώμα** ενός composable — τρέχει σε κάθε recomposition. Το `LaunchedEffect` τρέχει μια coroutine **όταν το composable μπει** στο composition (ή όταν αλλάξει το `key`):

```kotlin
@Composable
fun ProductScreen(id: String, vm: ProductViewModel = viewModel()) {
    LaunchedEffect(id) {          // τρέχει μια φορά ανά νέο id
        vm.load(id)
    }
    // ... render state
}
```

- `LaunchedEffect(Unit)` → τρέχει **μία φορά** (σαν `useEffect(..., [])`).
- `LaunchedEffect(id)` → ξανατρέχει όταν αλλάξει το `id` (σαν dependency array).
- Ακυρώνεται αυτόματα όταν το composable φύγει (structured concurrency).

Συγγενικά: `rememberCoroutineScope()` (για coroutines από event handlers, π.χ. `onClick`), `DisposableEffect` (cleanup όταν φεύγει το composable).

## Πώς απαντάς στη συνέντευξη

> «How does state work in Compose, and where should it live?»

> State in Compose is any observable value the UI reads; I create it with `remember { mutableStateOf(...) }`. `mutableStateOf` makes it observable so recomposition happens when it changes, and `remember` keeps it across recompositions — you need both. I keep composables as stateless as possible through state hoisting: a child takes its value as a parameter and reports changes with a callback, so state flows down and events flow up. That's unidirectional data flow, and it gives me reusable, testable components with a single source of truth. For anything beyond trivial UI state, I don't rely on `remember`, because it's lost when the Activity is recreated on rotation — `rememberSaveable` covers simple serializable values, but real app state and business logic belong in a `ViewModel`, which survives configuration changes. The ViewModel exposes a single immutable UI-state `data class` as a `StateFlow`, updated with `copy`, and the screen collects it with `collectAsStateWithLifecycle`. Side effects like loading data go in `LaunchedEffect` keyed appropriately, never in the composable body, which runs on every recomposition.
