# Testing & Production

Ένα Spring Boot app δεν είναι έτοιμο επειδή «τρέχει τοπικά». Πρέπει να είναι **δοκιμασμένο** (unit + integration tests) και **production-ready** (configuration ανά περιβάλλον, health/metrics, σωστό packaging). Αυτό το μάθημα κλείνει το track: **JUnit 5 + Mockito**, τα Spring test slices, **profiles**, το **Actuator**, και το πώς πακετάρεις & τρέχεις σε production.

## Τι πρέπει να μπορείς στο τέλος

- να γράφεις **unit tests** με JUnit 5 & **Mockito** (mock dependencies),
- να διακρίνεις unit vs **integration tests** (`@SpringBootTest` vs slices),
- να χρησιμοποιείς **profiles** για config ανά περιβάλλον,
- να εκθέτεις health/metrics με **Spring Boot Actuator**,
- να πακετάρεις ένα **executable JAR** και να το τρέχεις,
- να ξέρεις τις production βασικές (externalized config, secrets, logging).

## Unit tests: JUnit 5 + Mockito

Ένα **unit test** ελέγχει **μία** κλάση **απομονωμένα** — τα dependencies της γίνονται **mocks**. Η Java χρησιμοποιεί **JUnit 5** ως test framework και **Mockito** για mocking:

```java
class ProductServiceTest {

    @Test
    void returnsDiscountedPrice() {
        // Arrange — mock το dependency
        ProductRepository repo = mock(ProductRepository.class);
        when(repo.findById(1L)).thenReturn(Optional.of(new Product("Καφές", 10.0)));
        ProductService service = new ProductService(repo);

        // Act
        double result = service.priceWithDiscount(1L, 0.1);

        // Assert
        assertEquals(9.0, result);
        verify(repo).findById(1L);   // επιβεβαίωσε ότι κλήθηκε
    }
}
```

- `@Test` σημαίνει test method (JUnit 5 / Jupiter).
- `mock(...)` + `when(...).thenReturn(...)` = ορίζεις τη συμπεριφορά του fake dependency (**stubbing**).
- `assertEquals`/`assertThrows`/`assertTrue` = assertions.
- `verify(...)` = επιβεβαιώνεις interactions.

> Το DI που στήσαμε κάνει τα unit tests εύκολα: επειδή το `ProductService` δέχεται το repository στον constructor, περνάς ένα **mock** στο test — χωρίς βάση, χωρίς Spring, γρήγορο. Γι' αυτό το constructor injection είναι σημαντικό. Δομή: **Arrange-Act-Assert**.

## Integration tests & test slices

Τα unit tests δεν αρκούν — θέλεις να δοκιμάσεις ότι τα κομμάτια δουλεύουν **μαζί** (controller → service → DB). Το Spring δίνει διαβαθμίσεις:

| Annotation | Τι σηκώνει | Χρήση |
|---|---|---|
| `@SpringBootTest` | **ΟΛΟΚΛΗΡΟ** context | full integration (αργό) |
| `@WebMvcTest` | μόνο το web layer (controllers) | test controllers με mock services |
| `@DataJpaTest` | μόνο JPA/repository layer | test queries σε in-memory DB |

```java
@WebMvcTest(ProductController.class)
class ProductControllerTest {
    @Autowired MockMvc mockMvc;
    @MockBean ProductService service;   // mock το service layer

    @Test
    void returns404WhenMissing() throws Exception {
        when(service.findById(99L)).thenThrow(new ProductNotFoundException());
        mockMvc.perform(get("/api/products/99"))
               .andExpect(status().isNotFound());
    }
}
```

> **Test slices** (`@WebMvcTest`/`@DataJpaTest`) σηκώνουν **μόνο** το σχετικό κομμάτι του context — πολύ πιο γρήγορα από το `@SpringBootTest` που φορτώνει τα πάντα. Κανόνας (test pyramid): **πολλά** γρήγορα unit tests, **λιγότερα** slice/integration, **ελάχιστα** full end-to-end. Χρησιμοποίησε `@SpringBootTest` μόνο όταν χρειάζεσαι πραγματικά όλο το context.

## Profiles — config ανά περιβάλλον

Τα **profiles** επιτρέπουν διαφορετική configuration ανά περιβάλλον (dev/test/prod):

```
application.properties           # κοινά defaults
application-dev.properties       # τοπική ανάπτυξη (H2, verbose logging)
application-prod.properties      # production (PostgreSQL, minimal logging)
```

```properties
# application-prod.properties
spring.datasource.url=jdbc:postgresql://prod-db:5432/shop
spring.jpa.hibernate.ddl-auto=validate
logging.level.root=WARN
```

Ενεργοποιείς με `spring.profiles.active=prod` (env var ή flag). Μπορείς επίσης να έχεις beans που υπάρχουν **μόνο** σε ένα profile με `@Profile("dev")`.

> Το μοτίβο: **ένα** build artifact, **διαφορετική** config ανά περιβάλλον — δεν ξαναχτίζεις το app για prod. Αυτό δένει με το «externalized configuration» (12-factor): οι ρυθμίσεις έρχονται από environment, όχι hardcoded στον κώδικα.

## Spring Boot Actuator

Το **Actuator** εκθέτει **production-ready** endpoints για monitoring & management — χωρίς να τα γράψεις εσύ:

```
GET /actuator/health     → { "status": "UP" }   (liveness/readiness)
GET /actuator/metrics    → JVM memory, HTTP requests, DB pool...
GET /actuator/info       → build/version info
```

- **`/health`** — χρησιμοποιείται από load balancers/Kubernetes probes για να ξέρουν αν το app είναι ζωντανό/έτοιμο.
- **`/metrics`** — τροφοδοτεί monitoring (Prometheus/Grafana).

> Το health endpoint είναι ό,τι ρωτά ένα orchestrator (readiness/liveness probe — το είδες στο containers μάθημα): αν επιστρέψει `DOWN`, το Kubernetes σταματά να στέλνει traffic ή κάνει restart. Πρόσεχε την **έκθεση**: μην εκθέτεις ευαίσθητα actuator endpoints δημόσια χωρίς security.

## Packaging & running

Το Spring Boot πακετάρει σε **executable JAR** — με τον embedded server **μέσα**:

```bash
./mvnw clean package          # ή ./gradlew build → φτιάχνει target/app.jar
java -jar target/app.jar      # τρέχει· ο Tomcat είναι μέσα, χωρίς external server
```

Αυτό το «**fat JAR**» (περιέχει όλες τις εξαρτήσεις + server) είναι που κάνει το deployment απλό: ένα αρχείο, `java -jar`, τρέχει παντού όπου υπάρχει JVM — ιδανικό για Docker (`FROM eclipse-temurin`, `COPY app.jar`, `ENTRYPOINT java -jar`).

Production checklist που πρέπει να ξέρεις:
- **Externalized config & secrets:** DB passwords/keys από env vars, **όχι** στο properties/git.
- **Profiles:** `prod` profile ενεργό, `ddl-auto=validate` (όχι `create`/`update` σε prod!).
- **Logging:** structured, σωστά levels, όχι sensitive data.
- **Observability:** Actuator health/metrics + monitoring.

## Πώς απαντάς στη συνέντευξη

> «How do you test and productionize a Spring Boot app?»

> I test in layers following the pyramid. Unit tests use JUnit 5 and Mockito: because my classes take dependencies through the constructor, I pass mocks, stub them with `when(...).thenReturn(...)`, and assert the logic in isolation — no database, fast and deterministic. For wiring I use Spring's test slices rather than always booting the whole app: `@WebMvcTest` with `MockMvc` for controllers, `@DataJpaTest` for repository queries against an in-memory DB, and `@SpringBootTest` only when I genuinely need the full context. For production, configuration is externalized via profiles — `application-prod.properties` with the real datasource, `ddl-auto` set to validate, and secrets coming from environment variables, never committed. The same artifact runs in every environment; I just activate a profile. I expose Spring Boot Actuator for operations — `/health` for Kubernetes readiness and liveness probes, `/metrics` for monitoring — being careful not to expose sensitive endpoints publicly. Finally, Boot packages everything into an executable fat JAR with the embedded server inside, so deployment is just `java -jar app.jar`, which drops cleanly into a Docker image.
