# REST APIs

Το κύριο πράγμα που χτίζεις με Spring Boot είναι **REST APIs** — HTTP endpoints που σερβίρουν JSON στο frontend/mobile. Το Spring MVC κάνει την αντιστοίχιση HTTP → Java methods απλή με annotations, και προσθέτει **validation**, **exception handling** και σωστά **status codes**. Ξέρεις ήδη REST concepts από τα προηγούμενα tracks· εδώ τα βλέπεις στο Spring idiom.

Το ζητούμενο ποιότητας: ένα **καθαρό contract** — σωστά verbs & status codes, DTOs αντί να εκθέτεις entities, validation στην είσοδο, και **ενιαίο** error format.

## Τι πρέπει να μπορείς στο τέλος

- να ορίζεις endpoints με `@RestController` & request mappings,
- να διαβάζεις input με `@PathVariable`, `@RequestParam`, `@RequestBody`,
- να χρησιμοποιείς **DTOs** αντί να εκθέτεις entities,
- να κάνεις **validation** (`@Valid`, Bean Validation),
- να επιστρέφεις σωστά **status codes** (`ResponseEntity`),
- να στήνεις **centralized exception handling** (`@RestControllerAdvice`).

## `@RestController` & mappings

Ένα `@RestController` είναι bean που χειρίζεται HTTP requests και επιστρέφει **δεδομένα** (JSON), όχι HTML views:

```java
@RestController
@RequestMapping("/api/products")
public class ProductController {
    private final ProductService service;
    public ProductController(ProductService service) { this.service = service; }

    @GetMapping                              // GET /api/products
    public List<ProductDto> list() {
        return service.findAll();
    }

    @GetMapping("/{id}")                      // GET /api/products/42
    public ProductDto getOne(@PathVariable Long id) {
        return service.findById(id);
    }

    @PostMapping                             // POST /api/products
    @ResponseStatus(HttpStatus.CREATED)      // 201
    public ProductDto create(@Valid @RequestBody CreateProductRequest req) {
        return service.create(req);
    }
}
```

- `@GetMapping`/`@PostMapping`/`@PutMapping`/`@DeleteMapping` → HTTP verbs.
- `@RequestMapping("/api/products")` στην κλάση = κοινό prefix.
- Το return value σειριοποιείται **αυτόματα σε JSON** (μέσω Jackson).

## Διαβάζοντας input

| Annotation | Από πού | Παράδειγμα |
|---|---|---|
| `@PathVariable` | URL path | `/products/{id}` → `getOne(id)` |
| `@RequestParam` | query string | `/products?category=x` |
| `@RequestBody` | JSON body | POST/PUT payload |

```java
@GetMapping
public List<ProductDto> search(
    @RequestParam(required = false) String category,
    @RequestParam(defaultValue = "0") int page
) { ... }
```

Το `@RequestBody` κάνει **deserialize** το JSON σε Java object αυτόματα.

## DTOs — μην εκθέτεις entities

Κρίσιμο pattern: **μην** επιστρέφεις/δέχεσαι JPA **entities** απευθείας στο API. Χρησιμοποίησε **DTOs** (Data Transfer Objects) — συνήθως **records**:

```java
public record ProductDto(Long id, String title, double price) {}
public record CreateProductRequest(
    @NotBlank String title,
    @Positive double price
) {}
```

> Γιατί DTOs:
> - **Ασφάλεια:** τα entities μπορεί να έχουν πεδία που δεν πρέπει να εκτεθούν (password hash, internal flags).
> - **Απόζευξη:** το API contract δεν αλλάζει κάθε φορά που αλλάζει το DB schema.
> - **Lazy loading traps:** σειριοποιώντας entity με lazy σχέσεις μπορεί να πυροδοτήσεις N+1 ή `LazyInitializationException`.
> - **Validation:** ο request DTO κρατά τα validation rules της εισόδου, ξεχωριστά από το persistence model.

Το mapping entity↔DTO γίνεται στο service layer.

## Validation

Με **Bean Validation** (annotations στο DTO) + `@Valid`, το Spring ελέγχει την είσοδο **πριν** φτάσει στη logic:

```java
public record CreateProductRequest(
    @NotBlank(message = "Ο τίτλος είναι υποχρεωτικός") String title,
    @Positive double price,
    @Size(max = 500) String description
) {}

@PostMapping
public ProductDto create(@Valid @RequestBody CreateProductRequest req) { ... }
```

Αν το input αποτύχει, το Spring πετάει `MethodArgumentNotValidException` → by default **400 Bad Request**. Συχνά constraints: `@NotNull`, `@NotBlank`, `@Size`, `@Min`/`@Max`, `@Email`, `@Positive`.

## Status codes & `ResponseEntity`

Το REST contract θέλει **σωστά HTTP status codes**:

| Code | Πότε |
|---|---|
| `200 OK` | επιτυχές GET/PUT |
| `201 Created` | επιτυχές POST (νέο resource) |
| `204 No Content` | επιτυχές DELETE |
| `400 Bad Request` | invalid input |
| `404 Not Found` | δεν υπάρχει το resource |
| `409 Conflict` | π.χ. duplicate |

Για ρητό έλεγχο status/headers, χρησιμοποιείς **`ResponseEntity`**:

```java
@GetMapping("/{id}")
public ResponseEntity<ProductDto> getOne(@PathVariable Long id) {
    return service.findByIdOptional(id)
        .map(ResponseEntity::ok)                       // 200 + body
        .orElse(ResponseEntity.notFound().build());    // 404
}
```

## Centralized exception handling

Αντί για `try/catch` σε κάθε controller, ορίζεις **έναν** global handler με `@RestControllerAdvice` — ένα ενιαίο error format για όλο το API:

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(ProductNotFoundException.class)
    @ResponseStatus(HttpStatus.NOT_FOUND)
    public ErrorResponse handleNotFound(ProductNotFoundException ex) {
        return new ErrorResponse("PRODUCT_NOT_FOUND", ex.getMessage());
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)
    public ErrorResponse handleValidation(MethodArgumentNotValidException ex) {
        // μάζεψε τα field errors σε ένα καθαρό μήνυμα
        return new ErrorResponse("VALIDATION_ERROR", /* ... */);
    }
}

public record ErrorResponse(String code, String message) {}
```

> Όφελος: το business logic πετάει καθαρά **domain exceptions** (`ProductNotFoundException`), και ένα σημείο τα μεταφράζει σε σωστό HTTP status + συνεπές JSON error. Οι controllers μένουν λεπτοί, το frontend παίρνει **προβλέψιμο** error shape. Αυτό είναι το «καθαρό contract» που ελέγχεται στη συνέντευξη.

## Πώς απαντάς στη συνέντευξη

> «How do you build a REST API in Spring Boot?»

> I expose endpoints with a `@RestController` and map HTTP verbs with `@GetMapping`, `@PostMapping`, and so on, with a shared path prefix via `@RequestMapping`. Input comes in through `@PathVariable` for the URL, `@RequestParam` for the query string, and `@RequestBody` for the JSON payload, which Spring deserializes automatically, and return values are serialized back to JSON by Jackson. I never expose JPA entities directly — I map to DTOs, usually records, because entities can carry sensitive or internal fields, couple the API contract to the database schema, and drag in lazy-loading traps. Input is validated declaratively with Bean Validation annotations plus `@Valid`, so bad requests get a 400 before hitting my logic. I return correct status codes — 201 for a created resource, 204 for delete, 404 when missing — using `@ResponseStatus` or `ResponseEntity` for explicit control. And rather than try/catch in every controller, I centralize error handling in a `@RestControllerAdvice`: my services throw clean domain exceptions, and one place translates them into the right HTTP status and a consistent JSON error shape, so controllers stay thin and clients get a predictable contract.
