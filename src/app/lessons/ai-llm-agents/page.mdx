# Agents σε βάθος: loop, context & όρια

Στο μάθημα tool use είδες τον βασικό κύκλο: το μοντέλο ζητά εργαλείο, εσύ εκτελείς, επαναλαμβάνεις. Αυτό είναι ο **σκελετός** ενός agent. Ό,τι κάνει τη διαφορά ανάμεσα σε ένα demo και σε κάτι που δουλεύει σε production είναι **τα υπόλοιπα**: πότε *δεν* θέλεις agent, πώς σχεδιάζεις την επιφάνεια των εργαλείων, πώς διαχειρίζεσαι το context όταν το task τρέχει επί ώρες, και πού βάζεις τους ανθρώπους στη μέση. Αυτό το μάθημα καλύπτει αυτά.

## Πρώτα: μήπως δεν χρειάζεσαι agent;

Το πιο συχνό λάθος είναι να ξεκινάς από τον agent. Υπάρχουν **τρία επίπεδα**, και θέλεις το απλούστερο που λύνει το πρόβλημα:

| Επίπεδο | Τι είναι | Πότε |
|---|---|---|
| **Single call** | Ένα request, μία απάντηση | Classification, summarization, extraction, Q&A |
| **Workflow** | Πολλά βήματα, αλλά **ο κώδικάς σου** ορίζει τη σειρά | Pipeline με γνωστά στάδια |
| **Agent** | Το **μοντέλο** αποφασίζει τη διαδρομή του | Ανοιχτό task, μη προβλέψιμα βήματα |

Πριν πας στο τρίτο επίπεδο, έλεγξε **τέσσερα** κριτήρια — αν κάποιο πέφτει, μείνε πιο χαμηλά:

- **Πολυπλοκότητα** — είναι το task πολυβηματικό και δύσκολο να το προδιαγράψεις πλήρως εκ των προτέρων; («κάνε αυτό το design doc PR» ναι· «βγάλε τον τίτλο από αυτό το PDF» όχι.)
- **Αξία** — δικαιολογεί το αποτέλεσμα το κόστος και το latency; Ένας agent κάνει πολλαπλάσιες κλήσεις.
- **Εφικτότητα** — τα πάει καλά το μοντέλο σε αυτό το είδος εργασίας;
- **Κόστος λάθους** — μπορείς να **πιάσεις** και να **αναιρέσεις** τα λάθη; (tests, review, rollback)

> Αν ένα workflow με σταθερά βήματα δίνει το ίδιο αποτέλεσμα, ο agent είναι απλώς πιο ακριβός και πιο απρόβλεπτος τρόπος να το πετύχεις.

## Τι ακριβώς είναι το harness

Ο **agent loop** είναι δέκα γραμμές κώδικα. Το **harness** είναι όλα τα υπόλοιπα γύρω του:

```txt
harness = ο loop
        + η επιφάνεια των εργαλείων (ποια tools, με τι schema)
        + η διαχείριση του context (τι μένει, τι φεύγει, τι θυμάται)
        + τα permissions (τι εκτελείται αυτόματα, τι θέλει έγκριση)
        + το sandbox (πού τρέχει, τι μπορεί να αγγίξει)
        + observability (τι λογάρεις, πώς κάνεις debug)
```

Όταν διαλέγεις πώς θα χτίσεις, στην ουσία απαντάς σε **δύο ανεξάρτητες ερωτήσεις**: ποιος δίνει το harness, και ποιος τρέχει την υποδομή.

| Προσέγγιση | Γράφεις | Harness / Υποδομή |
|---|---|---|
| **Χειροκίνητος loop** | τον loop και τα tools | δικά σου και τα δύο |
| **Tool runner** (SDK helper) | μόνο τις συναρτήσεις των tools | harness από το SDK· υποδομή δική σου |
| **Managed agents** | config + τα δικά σου tool results | harness **και** υποδομή από τον provider |
| **Έτοιμο agent SDK** | ένα prompt + options | έτοιμο harness με built-in tools· υποδομή δική σου |

Ο χειροκίνητος loop **δεν** είναι απαραίτητος για approval gates ή logging — τα σύγχρονα tool runners δίνουν hooks ανά γύρο για ακριβώς αυτό. Κράτα τον χειροκίνητο loop για όταν θες να ελέγχεις **ολόκληρη** τη ροή.

## Σχεδιάζοντας την επιφάνεια των εργαλείων

Εδώ κρίνεται η ποιότητα ενός agent. Η βασική επιλογή: **ένα γενικό `bash` tool** ή **πολλά εξειδικευμένα tools**;

Το `bash` δίνει τεράστια ευελιξία — ο agent κάνει σχεδόν οτιδήποτε. Αλλά δίνει στο harness σου **ένα αδιαφανές string**, ίδιο για κάθε ενέργεια. Δεν μπορείς να ξεχωρίσεις ένα ακίνδυνο `grep` από ένα `git push`.

Προάγεις μια ενέργεια σε **δικό της tool** όταν θες:

- **Όριο ασφαλείας** — μη αναστρέψιμες ενέργειες (αποστολή email, διαγραφή, πληρωμή) θέλουν gate. Ένα `send_email` tool μπλοκάρεται εύκολα· ένα `bash -c "curl -X POST ..."` όχι.
- **Έλεγχο συνέπειας** — ένα `edit` tool μπορεί να **απορρίψει** εγγραφή αν το αρχείο άλλαξε από την τελευταία ανάγνωση. Το bash δεν μπορεί να εγγυηθεί τίποτα τέτοιο.
- **Ειδικό rendering** — μια «ερώτηση προς τον χρήστη» ως tool μπορεί να γίνει modal με κουμπιά.
- **Παραλληλισμό** — μπορείς να σημάνεις τα read-only tools ως ασφαλή για παράλληλη εκτέλεση. Μέσα από bash, το harness δεν ξεχωρίζει το `grep` από το `git push`, οπότε πρέπει να τα σειριοποιήσει όλα.

Πρακτικός κανόνας: **ξεκίνα με bash για εύρος· προάγαγε σε ειδικό tool όταν χρειάζεσαι gate, rendering, audit ή παραλληλισμό.** Και σε κάθε περίπτωση, γράψε το description **πότε** να καλείται, όχι μόνο τι κάνει — αυτό είναι ο μεγαλύτερος μοχλός στο αν το tool θα κληθεί σωστά.

## Context management: ο πραγματικός περιοριστικός πόρος

Ένας agent που τρέχει επί ώρες γεμίζει το context window με παλιά tool results. Υπάρχουν **τρία διαφορετικά** εργαλεία, και συχνά τα χρειάζεσαι και τα τρία:

| Τεχνική | Τι κάνει | Πότε |
|---|---|---|
| **Context editing** | **Σβήνει** παλιά tool results / thinking blocks | Το ιστορικό μπαγιατεύει μέσα στο ίδιο session |
| **Compaction** | **Συνοψίζει** το παλιό ιστορικό σε περίληψη | Πλησιάζεις το όριο του context window |
| **Memory** | Γράφει σε **αρχεία** που επιβιώνουν | Πρέπει να θυμάται **μεταξύ** sessions |

Η διαφορά editing/compaction είναι «κόβω» vs «περιλαμβάνω». Το πρώτο κρατά τη δομή της συνομιλίας και πετά ό,τι δεν χρειάζεται πια· το δεύτερο συμπυκνώνει. Το memory είναι άλλη κατηγορία: επιμονή **πέρα** από τη συνομιλία, σε filesystem που ο agent διαβάζει και γράφει.

> **Κρίσιμη λεπτομέρεια στο compaction:** πρέπει να προσθέτεις **ολόκληρο** το `response.content` πίσω στο ιστορικό, όχι μόνο το κείμενο. Τα compaction blocks είναι μέρος του content και το API τα χρειάζεται για να αντικαταστήσει το συμπυκνωμένο ιστορικό στο επόμενο request. Αν κρατάς μόνο το `.text`, χάνεις σιωπηλά την κατάσταση.

Παράλληλα, όταν τα tools είναι δεκάδες, μη τα φορτώνεις όλα: με **tool search** ο agent ανακαλύπτει μόνο τα σχετικά schemas. Και επειδή τα schemas *προστίθενται* αντί να αντικαθίστανται, δεν σπάει το cache — δες αμέσως παρακάτω γιατί έχει σημασία.

## Caching: γιατί ένας agent χωρίς αυτό κοστίζει πολλαπλάσια

Κάθε γύρος του loop ξαναστέλνει **όλο** το ιστορικό. Χωρίς prompt caching πληρώνεις το ίδιο prefix ξανά και ξανά. Το caching είναι **prefix match**: οτιδήποτε αλλάξει σε ένα byte ακυρώνει ό,τι είναι από εκεί και κάτω. Η σειρά είναι `tools` → `system` → `messages`.

Οι τρεις κανόνες που καθορίζουν αν ένας agent είναι φθηνός ή ακριβός:

- **Μην αλλάζεις τα tools στη μέση.** Τα tools είναι στη θέση 0 — προσθήκη, αφαίρεση ή αναδιάταξη ακυρώνει **τα πάντα**. Σειριοποίησέ τα ντετερμινιστικά (ταξινομημένα κατά όνομα).
- **Μην αλλάζεις μοντέλο στη μέση.** Τα caches είναι ανά μοντέλο. Θες φθηνότερο μοντέλο για ένα υπο-task; Κάνε **subagent**, κράτα τον κύριο loop σε ένα μοντέλο.
- **Πάγωσε το system prompt.** Ένα `new Date()` ή ένα user id μέσα στο system prompt ακυρώνει ό,τι έρχεται μετά — δηλαδή τα πάντα. Δυναμικό context μπαίνει **αργότερα**, στα `messages`.

Έλεγχος: αν το `usage.cache_read_input_tokens` είναι μηδέν σε επαναλαμβανόμενα requests, κάτι ακυρώνει σιωπηλά το cache.

## Subagents: πότε βοηθούν και πότε καίνε λεφτά

Ένας subagent είναι ένας δεύτερος agent loop για ένα υπο-task, με **δικό του** context. Η αξία: το κύριο context μένει καθαρό — παίρνεις πίσω μόνο το συμπέρασμα, όχι τα 40 tool results που το παρήγαγαν.

Το κόστος όμως είναι πραγματικό: κάθε subagent **ξαναχτίζει το context του από την αρχή**, ξανα-εξερευνά, γράφει αναφορά, και μετά ο συντονιστής τη διαβάζει. Αξίζει όταν:

- Τα υπο-tasks είναι **πραγματικά ανεξάρτητα** και τρέχουν παράλληλα (π.χ. ψάξιμο σε πολλά αρχεία ταυτόχρονα).
- Το υπο-task παράγει **πολύ θόρυβο** και λίγο σήμα.

Δεν αξίζει για δουλειά που ο κύριος agent τελειώνει σε λίγες κλήσεις, ούτε για επαλήθευση — ο έλεγχος ανήκει στον κύριο loop. Πρακτικά: βάλε **ρητό όριο** στον αριθμό των subagents.

## Άνθρωποι στη μέση & blast radius

Ο δικός σου κώδικας εκτελεί — άρα ο δικός σου κώδικας αποφασίζει. Τα τρία επίπεδα ελέγχου:

```txt
1. Permissions ανά tool:  always_allow | ask | deny
2. Sandbox:               πού τρέχει (container, VM, περιορισμένος χρήστης)
3. Credentials:           least privilege, ποτέ μέσα στο περιβάλλον εκτέλεσης
```

Το κριτήριο για το «ask» είναι η **αναστρεψιμότητα**: μια εγγραφή σε temp αρχείο είναι αναστρέψιμη, ένα email που έφυγε δεν είναι. Και αν ο agent τρέχει shell εντολές, θεώρησέ τες **μη έμπιστο input**: allowlist εκτελέσιμων, απόρριψη shell operators (`&&`, `|`, `;`), timeouts, logging. Ένα blocklist δεν αρκεί.

## Πού σπάνε οι agents στην πράξη

| Αστοχία | Τι βλέπεις | Αντίμετρο |
|---|---|---|
| Ατέρμονος loop | Ίδιες κλήσεις ξανά και ξανά | `max_iterations`, ανίχνευση επανάληψης |
| Σιωπηλό σφάλμα tool | Ο agent «συνεχίζει» με λάθος δεδομένα | Επίστρεψε `is_error: true` με μήνυμα — μην πετάς το αποτέλεσμα |
| Σπασμένα parallel results | Το μοντέλο σταματά να κάνει παράλληλες κλήσεις | Όλα τα `tool_result` σε **ένα** user message |
| Χαμένο cache | Το κόστος εκτοξεύεται χωρίς λόγο | Έλεγξε `cache_read_input_tokens`· ψάξε timestamps/UUID στο prefix |
| Context overflow | Κόβεται στη μέση, `max_tokens` | Compaction + context editing· μεγαλύτερο `max_tokens` |
| Παύση σε server-side tool | `stop_reason: "pause_turn"` | Ξαναστείλε το ιστορικό ως έχει — **χωρίς** νέο «Continue» μήνυμα |
| Αόρατη αποτυχία | Δεν ξέρεις τι έκανε | Λογάρισε κάθε tool call, input, result και το usage ανά γύρο |

> Το `pause_turn` μπερδεύει: δεν είναι λάθος. Σημαίνει ότι ο server-side κύκλος έφτασε το όριο επαναλήψεων. Ξαναστέλνεις το μήνυμα και το assistant content ως έχουν — το API καταλαβαίνει μόνο του ότι συνεχίζει.

## Πώς απαντάς στη συνέντευξη

> «How do you build an agent that actually works in production?»

> First, I check whether it should be an agent at all. There are three tiers — single call, workflow where my code owns the sequence, and agent where the model owns it — and I take the simplest one that works. An agent is justified when the task is genuinely open-ended, the value covers the extra cost and latency, the model is capable at it, and errors are catchable and reversible. The loop itself is trivial; the harness is the work. Tool surface first: bash gives breadth but hands the harness an opaque string, so I promote an action to a dedicated tool when I need to gate it, render it, audit it, or run it in parallel — and every description says *when* to call it, not just what it does. Then context, which is the real limiting resource: context editing clears stale tool results, compaction summarises when I'm near the window, and memory is files that survive across sessions — different tools, often all three. Caching is what makes the economics work, and it's a prefix match, so the rules are: don't change tools or the model mid-session, and never interpolate a timestamp into the system prompt — I verify with `cache_read_input_tokens`. Subagents keep the main context clean but each one rebuilds context from scratch, so I cap them and never use them for verification. Safety lives in my executor: per-tool permissions with approval on anything irreversible, a sandbox, and least-privilege credentials that never enter the execution environment. And I cap iterations, return `is_error` instead of swallowing tool failures, and log every call — an agent you can't inspect is one you can't debug.
