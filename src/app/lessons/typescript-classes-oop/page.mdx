# Classes & OOP στο TypeScript

Στη JavaScript ξέρεις ήδη τι είναι μια class. Το TypeScript προσθέτει από πάνω ένα ολόκληρο στρώμα: **access modifiers**, `readonly`, parameter properties, `implements`, `abstract`, generic classes. Θα τα συναντήσεις σε NestJS, Angular, TypeORM, σε παλιότερα codebases και σε συνεντεύξεις με backend/OOP βάρος — ακόμα κι αν στη React καθημερινότητά σου γράφεις κυρίως functions. Το μάθημα κλείνει με το πιο χρήσιμο κομμάτι: **πότε ΔΕΝ θέλεις class**.

## Typed properties & constructor

```ts
class Task {
  id: string;
  title: string;
  done: boolean = false;   // default τιμή

  constructor(id: string, title: string) {
    this.id = id;
    this.title = title;
  }
}
```

Με `strict` (συγκεκριμένα `strictPropertyInitialization`), κάθε property πρέπει να πάρει τιμή είτε στη δήλωση είτε στον constructor — αλλιώς ο compiler διαμαρτύρεται. Αν όντως αρχικοποιείται αλλού (π.χ. από framework), το δηλώνεις με `!`: `title!: string`.

## Access modifiers — `public`, `private`, `protected`

| Modifier | Πρόσβαση από | Υπάρχει στη runtime; |
|---|---|---|
| `public` (default) | παντού | — |
| `protected` | η class **και οι υποκλάσεις** | όχι (compile-time μόνο) |
| `private` | **μόνο** μέσα στην ίδια class | όχι (compile-time μόνο) |
| `#field` (JS) | μόνο μέσα στην class | **ναι** — αληθινά ιδιωτικό |

```ts
class Account {
  public owner: string;
  protected balance = 0;    // βλέπουν και οι υποκλάσεις
  private pin = "1234";     // μόνο εδώ — αλλά μόνο στο compile
  #secret = "real-private"; // JS private field — και στη runtime

  constructor(owner: string) {
    this.owner = owner;
  }
}

const a = new Account("Ada");
a.pin;                      // ❌ compile error
(a as any).pin;             // 😈 δουλεύει στη runtime — το private είναι erased
```

Κρίσιμη λεπτομέρεια για συνέντευξη: το `private` του TypeScript **εξαφανίζεται στο compile** (όπως κάθε type). Προστατεύει από λάθη συναδέλφων, όχι από κακόβουλο κώδικα. Αν θες **αληθινή** ιδιωτικότητα στη runtime, χρησιμοποιείς τα `#private` fields της JavaScript.

## Parameter properties — η συντομογραφία

Επειδή το «γράψε το πεδίο, γράψε την παράμετρο, κάνε την ανάθεση» είναι κουραστικό, το TypeScript δίνει συντομογραφία: **βάλε modifier στην παράμετρο του constructor** και το πεδίο δημιουργείται & ανατίθεται αυτόματα:

```ts
class Task {
  constructor(
    public readonly id: string,
    public title: string,
    private createdAt: Date = new Date(),
  ) {}
}

// ισοδύναμο με 8 γραμμές boilerplate
const t = new Task("1", "Μάθε TS");
t.id = "2"; // ❌ readonly
```

Αυτό ακριβώς το pattern βλέπεις παντού σε **NestJS/Angular dependency injection**: `constructor(private readonly userService: UserService) {}`.

## `readonly` properties

Το `readonly` επιτρέπει ανάθεση **μόνο** στη δήλωση ή στον constructor:

```ts
class Config {
  readonly url: string;
  constructor(url: string) {
    this.url = url;   // ✅ επιτρέπεται εδώ
  }
  reset() {
    this.url = "";    // ❌ error
  }
}
```

Είναι compile-time έλεγχος (όχι `Object.freeze`) — αλλά αρκεί για να δηλώσεις πρόθεση και να πιάσεις κατά λάθος μεταλλάξεις.

## `implements` — η class τηρεί ένα contract

Ένα interface περιγράφει το σχήμα· το `implements` λέει «αυτή η class **υποχρεούται** να το τηρεί»:

```ts
interface Repository<T> {
  findById(id: string): Promise<T | null>;
  save(item: T): Promise<void>;
}

class TaskRepository implements Repository<Task> {
  async findById(id: string): Promise<Task | null> { /* ... */ return null; }
  async save(item: Task): Promise<void> { /* ... */ }
  // αν ξεχάσεις μέθοδο ή αλλάξεις signature → compile error
}
```

Προσοχή στη διαφορά με τα άλλα γλωσσικά μοντέλα: λόγω **structural typing**, μια class ταιριάζει στο `Repository<Task>` ακόμα κι αν *δεν* γράψεις `implements`. Το `implements` δεν αλλάζει τους τύπους — είναι **έλεγχος πρόθεσης**: σε πιάνει στο σημείο της class αντί στο σημείο της χρήσης. Γι' αυτό αξίζει να το γράφεις.

## `extends` vs `implements`

| | `extends` | `implements` |
|---|---|---|
| Τι κληρονομεί | **implementation** + types | **μόνο** το contract |
| Πόσα | μία class | όσα interfaces θες |
| Runtime | ναι (πρωτότυπο) | όχι — εξαφανίζεται |

```ts
class Base { greet() { return "hi"; } }
class Child extends Base implements Serializable, Loggable {
  // παίρνει το greet() από το Base, υποχρεούται στα δύο interfaces
}
```

## `abstract` — μερική βάση

Μια `abstract` class **δεν** μπορεί να γίνει `new`. Ορίζει κοινή implementation + «τρύπες» που πρέπει να γεμίσουν οι υποκλάσεις:

```ts
abstract class Shape {
  abstract area(): number;          // χωρίς σώμα — υποχρεωτικό στις υποκλάσεις
  describe(): string {              // κοινή implementation
    return `Εμβαδόν: ${this.area()}`;
  }
}

class Circle extends Shape {
  constructor(private radius: number) { super(); }
  area(): number { return Math.PI * this.radius ** 2; }
}

new Shape();        // ❌ Cannot create an instance of an abstract class
new Circle(2).describe(); // ✅
```

Κανόνας επιλογής: **interface** όταν θες μόνο σχήμα· **abstract class** όταν θες να μοιραστείς και κώδικα.

## `static`, getters & setters

```ts
class User {
  static #count = 0;
  static fromJson(json: string): User {   // factory — δεν χρειάζεται instance
    return new User(JSON.parse(json).name);
  }

  constructor(private _name: string) { User.#count++; }

  get name(): string { return this._name; }
  set name(value: string) {
    if (!value.trim()) throw new Error("empty name");
    this._name = value;
  }
}

const u = User.fromJson('{"name":"Ada"}');
u.name = "Grace";   // περνά από τον setter (validation)
```

Τα `static` μέλη ανήκουν στην **class**, όχι στο instance. Οι getters/setters φαίνονται σαν properties αλλά τρέχουν κώδικα — χρήσιμοι για validation και computed τιμές.

## Generic classes

Ό,τι ισχύει για generic functions ισχύει και για classes:

```ts
class Store<T extends { id: string }> {
  private items = new Map<string, T>();

  add(item: T): void { this.items.set(item.id, item); }
  get(id: string): T | undefined { return this.items.get(id); }
  all(): T[] { return [...this.items.values()]; }
}

const tasks = new Store<Task>();
tasks.add(new Task("1", "Μάθε TS"));
const found = tasks.get("1"); // τύπος: Task | undefined
```

## Narrowing με `instanceof`

Οι classes είναι από τα λίγα πράγματα που **υπάρχουν** στη runtime — γι' αυτό το `instanceof` δουλεύει ως type guard:

```ts
class ValidationError extends Error {
  constructor(public field: string, message: string) {
    super(message);
    this.name = "ValidationError";
  }
}

try {
  // ...
} catch (err) {              // τύπος: unknown (με strict)
  if (err instanceof ValidationError) {
    console.log(err.field);  // ✅ narrowed
  } else if (err instanceof Error) {
    console.log(err.message);
  }
}
```

Custom error classes είναι από τις πιο πρακτικές χρήσεις των classes σε fullstack κώδικα.

## Πότε ΔΕΝ θέλεις class

Το πιο συχνό λάθος όσων έρχονται από Java/C#: να γίνονται όλα class. Στη σύγχρονη TypeScript/React καθημερινότητα:

- **Data χωρίς συμπεριφορά** → `interface` / `type` + plain object. Ένα `Task` που απλώς κρατά πεδία δεν χρειάζεται class (και τα plain objects είναι απευθείας JSON-serializable — τα class instances χάνουν τις μεθόδους τους σε `JSON.stringify`/`parse`).
- **Λογική χωρίς κατάσταση** → σκέτες functions, ευκολότερα σε test και tree-shaking.
- **React components** → function components· οι class components είναι legacy.

Οι classes αξίζουν όταν έχεις **κατάσταση + συμπεριφορά μαζί** και πολλά instances: repositories, services, custom errors, clients με σύνδεση, μικρές μηχανές κατάστασης.

## Πώς απαντάς στη συνέντευξη

> «What does TypeScript add to JavaScript classes, and when do you use them?»

> Type annotations on fields and methods, plus access modifiers — `public`, `protected`, `private` — and `readonly`. The important caveat is that those modifiers are compile-time only: `private` is erased, so `(obj as any).field` still reads it at runtime; if I need real privacy I use JavaScript's `#` fields. Parameter properties are the shorthand you see everywhere in NestJS and Angular — a modifier on a constructor parameter declares and assigns the field in one go. `implements` checks that a class honours an interface; because TypeScript is structural the class would be compatible anyway, but `implements` moves the error to the class instead of the call site. `extends` inherits implementation and you get only one; `implements` is contract-only and you can have many. `abstract` classes sit in between — shared code plus methods subclasses must fill in. As for when: I don't reach for classes by default. Plain objects with interfaces for data, plain functions for stateless logic — they're simpler to test and JSON-serialize cleanly. Classes earn their place when state and behaviour belong together: repositories, service clients, and custom error types, where `instanceof` gives me real runtime narrowing.
