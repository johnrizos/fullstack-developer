# Setup, Compiler & Καθημερινό Workflow

Πριν γράψεις σοβαρό TypeScript, πρέπει να ξέρεις **πώς τρέχει**. Αυτό το μάθημα καλύπτει ό,τι συνήθως θεωρείται «δεδομένο» και σε αφήνει να ψάχνεις: πώς εγκαθιστάς και τρέχεις TS, τι ακριβώς κάνει ο `tsc`, τι σημαίνει κάθε πεδίο στο `tsconfig.json`, πώς **διαβάζεις** ένα error message, `import type`, και πώς σιωπάς έναν έλεγχο χωρίς να χαλάσεις την ασφάλεια.

## Εγκατάσταση & πρώτο τρέξιμο

Το TypeScript είναι ένα npm package — **dev dependency**, γιατί χρειάζεται μόνο κατά την ανάπτυξη:

```bash
npm i -D typescript          # ο compiler
npx tsc --init               # δημιουργεί tsconfig.json με σχόλια
npx tsc                      # compile: .ts -> .js (και type check)
npx tsc --watch              # ξανατρέχει σε κάθε αλλαγή αρχείου
npx tsc --noEmit             # ΜΟΝΟ type check, χωρίς να παράγει αρχεία
```

Το `npx` τρέχει το τοπικά εγκατεστημένο binary από το `node_modules/.bin` — γι' αυτό δεν χρειάζεται global install (και δεν το θέλεις: κάθε project θέλει τη δική του έκδοση TS).

## Πώς «τρέχεις» ένα .ts αρχείο

Το Node **δεν** καταλαβαίνει `.ts` όπως-όπως. Έχεις τρεις τυπικές διαδρομές:

| Διαδρομή | Πώς | Πότε |
|---|---|---|
| Compile & run | `npx tsc && node dist/index.js` | Node backend, βιβλιοθήκες |
| Direct run | `npx tsx src/index.ts` | scripts, γρήγορο dev |
| Framework | Next.js / Vite το κάνουν μόνα τους | frontend apps |

Το [`tsx`](https://www.npmjs.com/package/tsx) (και το παλαιότερο `ts-node`) τρέχουν το αρχείο χωρίς χωριστό build βήμα. Στις νεότερες εκδόσεις του Node υπάρχει και built-in type stripping, αλλά το `tsx` παραμένει η πιο ανώδυνη επιλογή σε projects.

## Η πιο σημαντική διάκριση: type checking ≠ build

Ο `tsc` κάνει **δύο** πράγματα: ελέγχει τύπους **και** παράγει JavaScript. Τα μοντέρνα εργαλεία (Next.js, Vite, esbuild, swc) όμως κάνουν μόνο το δεύτερο — **πετάνε** τους τύπους χωρίς να τους ελέγξουν, γιατί είναι δραματικά ταχύτερο.

> Πρακτική συνέπεια που σε τσιμπάει: το `npm run dev` μπορεί να δουλεύει μια χαρά ενώ ο κώδικας έχει type errors. Γι' αυτό κάθε σοβαρό project έχει ξεχωριστό script:
>
> ```json
> { "scripts": { "typecheck": "tsc --noEmit" } }
> ```
>
> …και το τρέχει στο CI. Ο editor σου δείχνει τα ίδια errors ζωντανά (τρέχει τον **tsserver**), αλλά ο editor βλέπει μόνο τα ανοιχτά αρχεία — το `tsc --noEmit` βλέπει ολόκληρο το project.

## tsconfig.json — τι σημαίνει κάθε πεδίο

Το `tsconfig.json` ορίζει **ποια αρχεία** ελέγχονται και **με ποιους κανόνες**. Δεν χρειάζεται να τα ξέρεις όλα (είναι 100+), αλλά αυτά τα συναντάς παντού:

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "lib": ["ES2022", "DOM"],
    "module": "ESNext",
    "moduleResolution": "bundler",
    "jsx": "preserve",
    "strict": true,
    "noEmit": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "forceConsistentCasingInFileNames": true,
    "baseUrl": ".",
    "paths": { "@/*": ["./src/*"] }
  },
  "include": ["src"],
  "exclude": ["node_modules"]
}
```

- **`target`** — σε ποια έκδοση JavaScript μεταγλωττίζεται (π.χ. `ES2022`). Χαμηλό target = περισσότερο downleveling (το `async/await` γίνεται generators κ.λπ.). Για Node ή μοντέρνους browsers, `ES2022` είναι ασφαλές.
- **`lib`** — ποια **built-in APIs** ξέρει ο compiler. Χωρίς `"DOM"` δεν υπάρχει `document`/`window`. Ένα καθαρό Node project δεν βάζει DOM.
- **`module`** / **`moduleResolution`** — τι σύστημα modules παράγεται (`ESNext` = `import`/`export`, `CommonJS` = `require`) και πώς βρίσκονται τα imports. Σε Next.js/Vite: `"ESNext"` + `"bundler"`. Σε καθαρό Node: `"NodeNext"` και για τα δύο.
- **`jsx`** — πώς χειρίζεται JSX. `"preserve"` σημαίνει «άσ' το, θα το κάνει το framework».
- **`strict`** — η ομάδα αυστηρών ελέγχων (αναλυτικά στο μάθημα *Type Safety & tsconfig*). **Πάντα `true`.**
- **`noEmit`** — «μην παράγεις αρχεία, μόνο έλεγξε». Το βάζεις όταν το build το κάνει ο bundler.
- **`outDir` / `rootDir`** — πού πάει το παραγόμενο JS και πού είναι οι πηγές (όταν *δεν* έχεις `noEmit`).
- **`esModuleInterop`** — επιτρέπει `import express from "express"` για CommonJS packages, αντί για `import * as express`. Θέλεις `true`.
- **`skipLibCheck`** — παραλείπει τον έλεγχο μέσα στα `.d.ts` των dependencies. Κάνει το build πολύ ταχύτερο και σε γλιτώνει από errors σε κώδικα που δεν ελέγχεις. Σχεδόν πάντα `true`.
- **`baseUrl` / `paths`** — path aliases: `@/lib/x` αντί για `../../../lib/x`. Προσοχή: ο **bundler** πρέπει να ξέρει τα ίδια aliases (στο Next.js τα διαβάζει αυτόματα).
- **`include` / `exclude`** — ποια αρχεία μπαίνουν στο project. Το `exclude` **δεν** εξαιρεί αρχεία που κάποιο άλλο αρχείο κάνει import.
- **`allowJs`** / **`checkJs`** — επιτρέπει `.js` αρχεία μέσα στο project, και (προαιρετικά) τα ελέγχει. Χρήσιμο σε σταδιακή μετάβαση JS → TS.
- **`declaration`** — παράγει `.d.ts` για τη δική σου βιβλιοθήκη (μάθημα *Declaration Files*).

## `import type` — γιατί υπάρχει

Ένας τύπος δεν υπάρχει στη runtime. Όταν κάνεις import **μόνο** έναν τύπο, το `import type` το δηλώνει ρητά, ώστε το import να **σβήνεται** ολόκληρο στο compile:

```ts
import type { User } from "./models";     // εξαφανίζεται στο build
import { formatUser } from "./format";    // μένει — είναι κώδικας

import { type User, formatUser } from "./mixed"; // inline μορφή
export type { User };
```

Γιατί έχει σημασία: αποφεύγεις να τραβήξεις κατά λάθος ένα ολόκληρο module στο bundle μόνο για έναν τύπο, και γλιτώνεις κυκλικά imports. Με τη ρύθμιση **`verbatimModuleSyntax: true`** ο compiler σε **υποχρεώνει** να το γράφεις — γι' αυτό το βλέπεις παντού σε νέα projects.

## Πώς διαβάζεις ένα error message

Τα TS errors φαίνονται τρομακτικά επειδή είναι **αναδρομικά**: σου λένε το γενικό πρόβλημα και μετά σκάβουν προς το ακριβές σημείο. Διάβασέ τα **από κάτω προς τα πάνω** — η τελευταία γραμμή είναι η αλήθεια:

```text
Type '{ id: number; title: string; }' is not assignable to type 'Task'.
  Types of property 'id' are incompatible.
    Type 'number' is not assignable to type 'string'.
```

Μετάφραση: «το `id` σου είναι `number`, το `Task` θέλει `string`». Τρία μοτίβα που θα δεις συνέχεια:

| Μήνυμα | Τι σημαίνει |
|---|---|
| `Type 'X' is not assignable to type 'Y'` | Έδωσες X εκεί που περίμενε Y |
| `Property 'x' does not exist on type 'Y'` | Ή typo, ή ο τύπος είναι πιο στενός απ' ό,τι νομίζεις (συχνά θέλει narrowing) |
| `Object is possibly 'null' / 'undefined'` | Το `strictNullChecks` δουλεύει — χειρίσου το κενό |
| `Parameter 'x' implicitly has an 'any' type` | Το `noImplicitAny` — βάλε τύπο στην παράμετρο |

Κάθε error έχει και κωδικό (`TS2322`). Αν κολλήσεις, αυτός ο κωδικός + το μήνυμα είναι το καλύτερο search query.

## Πώς σιωπάς έναν έλεγχο — σωστά

Μερικές φορές ο compiler κάνει λάθος (ή περιμένεις fix από dependency). Υπάρχουν δύο σχόλια και **δεν** είναι ισοδύναμα:

```ts
// @ts-expect-error — περιμένουμε error εδώ· αν ΠΑΨΕΙ να υπάρχει, το σχόλιο γίνεται error
const x: number = "still a string";

// @ts-ignore — σβήνει το error σιωπηλά, για πάντα
const y: number = "still a string";
```

Το **`@ts-expect-error` είναι πάντα η σωστή επιλογή**: αυτοκαθαρίζεται. Όταν διορθωθεί η αιτία, ο compiler σου λέει «αυτό το σχόλιο δεν χρειάζεται πια» — ενώ ένα `@ts-ignore` μένει και κρύβει πραγματικά bugs χρόνια μετά. Και τα δύο ισχύουν **μόνο για την επόμενη γραμμή**.

## Πώς απαντάς στη συνέντευξη

> «How does TypeScript actually run in a modern project?»

> Two separate things: type checking and building. `tsc` does both, but modern tooling — Next.js, Vite, esbuild, swc — only strips the types for speed, it doesn't check them. So a dev server can be perfectly happy while the code has type errors. That's why I keep a `typecheck: tsc --noEmit` script and run it in CI; the editor shows the same errors live through tsserver, but only for open files. The config lives in `tsconfig.json` — the ones that matter day to day are `strict` (always on), `target`/`lib` for what JS and built-in APIs are assumed, `moduleResolution` matched to the runtime, `skipLibCheck` to avoid checking dependency type files, and `paths` for aliases. For imports I use `import type` for type-only imports so they're erased at build time, which `verbatimModuleSyntax` enforces. And when I genuinely need to silence the compiler I use `@ts-expect-error`, never `@ts-ignore`, because it errors once it's no longer needed.
