# Xcode, Signing & App Store

Έγραψες την app — τώρα πρέπει να **φτάσει σε συσκευές**. Το iOS deployment έχει ένα κομμάτι που μπερδεύει κάθε αρχάριο: το **code signing** και τα **provisioning profiles**. Η Apple απαιτεί κάθε app να είναι κρυπτογραφικά υπογεγραμμένη ώστε να ξέρει ποιος την έφτιαξε και σε ποιες συσκευές επιτρέπεται να τρέξει. Σε αυτό το μάθημα βλέπουμε τη διαδρομή από το Xcode μέχρι το App Store & το TestFlight.

## Τι πρέπει να μπορείς στο τέλος

- να καταλαβαίνεις το Xcode project, schemes και build configurations (Debug/Release),
- να εξηγείς τι είναι **bundle ID**, **certificate** και **provisioning profile**,
- να ξέρεις γιατί υπάρχει το **code signing** και τι λύνει,
- να δημιουργείς ένα **archive** και να το ανεβάζεις στο **App Store Connect**,
- να διανέμεις beta μέσω **TestFlight**,
- να κατανοείς το **App Store review** και το versioning.

## Xcode: project, schemes, configurations

Το **Xcode** είναι το IDE της Apple — build, run, debug, profiling, signing, όλα εκεί.

- **Scheme:** τι χτίζεται και πώς τρέχει (ποιο target, ποια configuration). Εναλλάσσεσαι scheme για να τρέξεις σε simulator vs device.
- **Build configuration:** τυπικά **Debug** και **Release**.
  - *Debug* — γρήγορο build, χωρίς optimizations, με debug symbols, για ανάπτυξη.
  - *Release* — optimized (`-O`), για διανομή. Ό,τι στέλνεις στο App Store είναι Release.
- **Target:** ένα προϊόν που παράγεται (η app, ένα widget extension, τα tests).

> Ξεχωριστές ρυθμίσεις ανά configuration (π.χ. διαφορετικό API base URL για dev vs prod) μπαίνουν με build settings / xcconfig / compilation conditions (`#if DEBUG`). Ό,τι φτάνει στους χρήστες πρέπει να χτίζεται σε **Release**.

## Bundle ID — η ταυτότητα της app

Το **bundle identifier** (π.χ. `com.giannis.shopapp`) είναι το μοναδικό, σταθερό όνομα της app σε όλο το οικοσύστημα της Apple. Χρησιμοποιείται σε signing, στο App Store Connect, στα push notifications, στα capabilities. **Δεν αλλάζει** μετά το πρώτο release — μια app με άλλο bundle ID είναι άλλη app.

## Code signing — γιατί υπάρχει

Η Apple απαιτεί κάθε binary που τρέχει σε πραγματική συσκευή να είναι **υπογεγραμμένο**. Δύο κομμάτια:

- **Signing certificate:** αποδεικνύει **ποιος** υπογράφει (εσύ / η ομάδα σου, μέσω του Apple Developer account). Development certificate για τοπικό testing, Distribution certificate για App Store.
- **Provisioning profile:** συνδέει τρία πράγματα — το **App ID** (bundle ID), το **certificate**, και (για development) τις επιτρεπόμενες **συσκευές** + τα **capabilities** (push, iCloud κ.λπ.). Λέει ουσιαστικά «αυτή η υπογεγραμμένη app επιτρέπεται να τρέξει εδώ».

> **Γιατί όλο αυτό;** Ασφάλεια & εμπιστοσύνη: ο χρήστης ξέρει ότι η app προέρχεται από ταυτοποιημένο developer και δεν έχει πειραχτεί μετά την υπογραφή. Στη πράξη, το **Xcode automatically managed signing** χειρίζεται certificates & profiles για σένα — απλώς διαλέγεις το Team σου. Το χειροκίνητο signing χρειάζεται σε πιο σύνθετα CI/enterprise setups.

Το **Apple Developer Program** (πληρωμένο, ετήσιο) είναι προϋπόθεση για signing που τρέχει σε συσκευές τρίτων και για δημοσίευση.

## Archive — το πακέτο διανομής

Όταν είσαι έτοιμος να διανείμεις, φτιάχνεις ένα **archive** (Product → Archive στο Xcode): ένα Release build υπογεγραμμένο για distribution. Το iOS πακετάρει την app ως **`.ipa`**. Από το Organizer window κάνεις **Distribute** → upload στο **App Store Connect**.

Στο upload εφαρμόζονται και optimizations όπως **app thinning** (η κάθε συσκευή κατεβάζει μόνο τα assets/architecture που χρειάζεται) και **bitcode/symbol** handling για crash symbolication.

## App Store Connect

Το **App Store Connect** (appstoreconnect.apple.com) είναι το web portal διαχείρισης:

- Δημιουργείς τη **record** της app (όνομα, bundle ID, κατηγορία).
- Ανεβάζεις **builds** (από το Xcode archive).
- Συμπληρώνεις **metadata**: screenshots, περιγραφή, keywords, privacy nutrition labels, age rating.
- Ρυθμίζεις **τιμή** & διαθεσιμότητα ανά χώρα.
- Υποβάλλεις για **review** και ελέγχεις analytics/crashes.

## TestFlight — beta distribution

Πριν το public release, το **TestFlight** μοιράζει beta builds:

- **Internal testers** (μέλη της ομάδας, έως 100) — άμεση διάθεση, χωρίς review.
- **External testers** (έως 10.000, με link/email) — απαιτούν σύντομο beta review.
- Κάθε build λήγει μετά από **90 μέρες**.

> Ροή που θα χρησιμοποιείς: archive → upload → μοίρασε internal TestFlight build στην ομάδα → μάζεψε feedback/crashes → επανάληψη → external beta → τελικό App Store submission. Έτσι πιάνεις προβλήματα σε πραγματικές συσκευές πριν φτάσουν στους χρήστες.

## App Store review & versioning

- Κάθε submission περνά **ανθρώπινο review** (App Review Guidelines): crashes, ελλιπής λειτουργικότητα, privacy παραβάσεις, παραπλανητικά metadata είναι συχνοί λόγοι rejection.
- **Versioning** — δύο αριθμοί (όπως στο Android):
  - **Version (marketing, π.χ. `1.2.0`)** — αυτό που βλέπει ο χρήστης (`CFBundleShortVersionString`).
  - **Build number (π.χ. `42`)** — εσωτερικός· πρέπει να **αυξάνει** σε κάθε upload για το ίδιο version (`CFBundleVersion`).
- Μετά την έγκριση διαλέγεις **manual** ή **automatic release**, και μπορείς να κάνεις **phased release** (σταδιακή διάθεση σε ποσοστό χρηστών σε 7 μέρες).

## Πώς απαντάς στη συνέντευξη

> «Walk me through shipping an iOS app to the App Store.»

> I build in Xcode, and everything that reaches users is the Release configuration — optimized, with distribution signing. The part people underestimate is code signing: Apple requires every binary on a real device to be signed. A signing certificate proves who I am via my Apple Developer account, and a provisioning profile ties the App ID — the bundle identifier — to that certificate and, for development, to allowed devices and capabilities, so the device knows the app is legitimate and untampered. In practice I let Xcode manage signing. To ship, I create an archive, which is a signed Release build, and upload it to App Store Connect, where I manage the app record, builds, and metadata. Before the public release I distribute betas through TestFlight — internal testers get it immediately, external testers after a short beta review — to catch issues on real devices. Then I submit for App Review. Versioning has two numbers: the marketing version users see, and a build number that must increase on every upload. After approval I can do a manual or phased release.
